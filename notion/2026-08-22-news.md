## 🎯 今天的主軸｜AI 寫程式的競賽，重點從「模型會不會寫」換成「一群代理在團隊裡怎麼被看見、被指揮、被把關」

把 AI coding 想成公司裡的一位新同事。過去兩年，它坐在你身邊、只跟你講話——你打字，它在你的編輯器裡幫你補完、回答，一次一個對話，你得盯著它。這個週末，這位同事被拉進了團隊的群組聊天室：全隊都看得到它在做什麼、都能插話指揮它，它自己跑去背景做事，做完把成果丟上來等人簽核。（比喻說回技術：拉進群組＝從 IDE 搬進 Slack／Teams 頻道；自己跑去背景＝在雲端沙盒裡非同步執行；等人簽核＝PR 合併前的人工審核門檻。）

**共同變化：** 8/21，GitHub Copilot 同時在 Slack 與 Microsoft Teams 上線代理體驗：在頻道裡 @GitHub，就能把一段對話變成「全隊都看得到、都能一起指揮」的雲端代理任務，代理會在安全沙盒裡調查失敗、改碼、驗證、開 PR。前一天（8/20）OpenAI Codex v0.149.0 加了 `codex agents` 互動儀表板（搜尋、啟動、開啟、改名、停止各項任務）與 `codex queue`（對本地或遠端正在跑的 session 非同步送訊息）。同一週 Anthropic Claude Code 讓多個工作階段之間用 `@` 直接喊話（跨階段 SendMessage、閒置通知），並補上 GitLab Merge Request 支援。三家、三個產品，長出的是同一個形狀。

**為什麼放在一起看：** 它們不約而同回答了同一個問題——當一個人可以同時開好幾個代理，這些代理該住在哪、怎麼管、誰負責？答案驚人一致：住在團隊已經在用的地方（Slack 頻道、Teams 討論串、PR）；給你一個看得到全部平行任務的視圖（Codex 儀表板、Slack Code 頻道）並能非同步下指令；把「合併要人核准」做成硬門檻（GitHub 兩個產品都讓管理員能要求 PR 額外核准）。單看一則都是小更新，擺在一起就是產業收斂到同一個設計：**代理當成共用、非同步的隊友，外面包一層人工把關**。

**過去 vs. 現在：** 一年前的 Copilot 是「你編輯器裡的自動補全與聊天視窗」——一個人、一個對話、同步等它回，成果只有你看得到。現在是：你在 Slack 頻道 @GitHub 丟一句「這 CI 為什麼掛了，修一下」，代理開一個全隊可見的任務，跑去沙盒調查、改碼、開 PR，你關掉視窗去開會，回來看計畫與 diff，覺得可以再按核准合併。工作的單位，從「我和 AI 的一次對話」變成「團隊和一群代理的一條可追蹤任務流」。

**背後邏輯：** 模型「會寫」已經不稀奇，瓶頸換了位置。當一個工程師能同時指揮五個代理，痛點不再是產出速度，而是這麼多平行產出誰看得到、怎麼審、出事算誰的。於是各家把力氣花在三件事：把代理放進團隊本來就會看的地方（可見性）、給一個管很多任務的儀表板（可控性）、把合併卡在人工核准（可歸責）。

> 👤 編輯分析：這其實是 AI coding 從「個人生產力工具」升級成「需要治理的團隊基礎設施」的轉折點。當一個能力開始把「怎麼被監督」寫進賣點（GitHub 的「human in the loop before agent-authored work ships」、xAI 的「with messaging, approvals」），代表它要從玩具進到生產線了。（此段為編輯觀點，非官方結論。）

**對你的工作：** 帶團隊的人，code review 與 PR 核准正在變成整條產線的控制閥——當一半 PR 是代理開的，審查頻寬會先撞牆，你需要「哪些改動代理可自主、哪些必須人審」的明確分級。工程師則值得現在就練「讀 diff、抓代理漏掉的 corner case」這種把關能力，它的稀缺度正在超過「自己把 code 寫出來」。

**限制與待驗證：** 別把「上線」當「解決」。人工核准門檻擋得住「技術上能合併」，擋不住「人其實沒細看就按了核准」。還沒被驗證的問題：團隊會認真審、還是很快淪為橡皮圖章？多代理在頻道跑的訊息噪音怎麼收斂？雲端沙盒用量另計費，成本會不會失控？都要幾季真實使用才知道。

> 💡 記住這句：2026 下半年 AI coding 的勝負手不再是「模型多會寫」，而是「一群代理在團隊裡怎麼被看見、被指揮、被把關」——而「代理自驗、人類簽核」這套邏輯，你在半導體驗證與 sign-off 裡早就熟得不能再熟。

## 📖 今日概念｜審核門檻（Human-in-the-loop / Approval Gate）

**定義：** 在一條自動化流程裡，刻意保留一個「非得由人類點頭才能繼續」的關卡。機器可以把事情做到 99%，但跨過某條高風險界線之前，一定要人簽核。

**生活化比喻：** 像公司的請款系統——金額系統自動算、表單自動填，但只要超過一定額度，就一定要主管簽核才會付錢。說回技術，這正是 GitHub 讓「代理開的 PR 一定要管理員核准才能合併」的設計：放手讓它做，卡住讓它別自己拍板。

**工作中的例子：** 代理在沙盒裡改完碼、跑完測試、開好 PR，但 `main` 分支的合併按鈕是鎖著的：要有寫入權限的人看過 diff、確認沒問題才放行。整個過程代理都能自己跑，唯獨「併進去」這一下留給人。

**常見誤解：** 以為 human-in-the-loop 就是「全程盯著 AI 做每一步」。其實現代設計多半是「非同步 + 只在關鍵節點把關」——平時放手讓代理自己跑，只在合併、上線、花錢這種高風險點攔一下。盯太多等於沒享受到自動化；完全不盯等於把責任也一起交出去。

**與今天主軸的關係：** 今天三家不約而同在代理外面包一層審核門檻，正是承認「讓代理自己動手」和「讓代理自己拍板」是兩件完全不同的事——前者能大膽放，後者要謹慎守。

## 🏭 半導體 AI 專區｜會自己驗證的 AI 代理，如何改寫晶片驗證的把關流程

**分類：** EDA 工具／驗證
**內容屬性：** 背景知識（非 48 小時內新聞；引用 2026 年 7 月 DAC 2026 的官方發表與廠商評估）

**問題與流程位置：** 驗證（verification）是 IC 設計最吃人力的環節之一，一個大專案常花掉一半以上工時。工程師寫 testbench、跑模擬、看波形、debug，反覆到「RTL 驗到夠乾淨、可以往下走」為止。它卡在流程中段：RTL 寫完之後、實體設計之前，是每一版設計都躲不掉的關卡。

**AI 如何介入（與過去的差別）：** 過去 AI 頂多幫你補幾條 testbench、或把失敗波形分類，都是「單點輔助」，每步還是等人下指令。背景（2026 年 7 月 DAC 2026）：Synopsys、Siemens 等把它推成「長時間自主運行的驗證代理」——交付一個目標，代理自己規劃驗證、跑迴歸、定位 bug、甚至改 testbench，把整個驗證迴圈串起來跑好幾輪。差別就在「從一步一步等指令，變成給目標、自己迭代」，正是今天軟體圈主軸的晶片版。

**資料與產出：** 輸入是 RTL、規格與驗證計畫；產出是覆蓋率報告、失敗根因與修正建議。Siemens 的做法特別點名「self-verifying」——代理把自己的產出，再對照物理引擎或黃金模型檢查一次，而不是自己說對就算對。

**如何驗證：** 這正是和今天主軸同一個道理——代理可以自己跑、自己初步驗證，但最終 sign-off 仍是人類與既有 golden flow 的責任。可能影響／廠商宣稱：Synopsys 曾宣稱其自主驗證代理「time-to-validated RTL 最快 50 倍」、在與 AMD／微軟的早期評估中「debug 週期減 25–40%」——這些是特定評估下的廠商數字，不是普遍量產結果，請當「可能影響」讀，別當保證。

**限制與風險：** 代理可能「答對但想錯」——覆蓋率數字漂亮，卻漏了關鍵 corner case；黑箱決策難稽核；廠商公布的加速比多來自挑過的情境。真正落地仍卡在資料品質、與既有 sign-off 流程的整合，以及「出事責任歸屬」。

> 👷 對半導體工作者的意義：驗證工程師的價值，正從「手寫 testbench、盯波形」往「設計驗證策略、審核代理的覆蓋率與根因、守住 sign-off 門檻」移動——就像軟體圈今天把重心從寫碼移到審碼。可以現在就做的一步：把你團隊「哪些驗證判斷絕不能讓 AI 自己拍板」的清單先寫下來。

## 🪞 反思時間

- 當「寫程式」被代理搬進團隊頻道、還能非同步同時跑好幾個，你的團隊真正稀缺的能力，會從「誰寫得快」變成什麼？你現在的招募與訓練，押對了那個新稀缺嗎？
- 如果明天你的 PR 有一半是代理開的，你現在的 code review 流程扛得住嗎？哪一個環節會先崩——是審查頻寬不夠，還是「大家其實沒細看就按了核准」？
- 軟體圈把「人類最後把關」做成了產品門檻；換到你的驗證或 tapeout 流程，哪些 sign-off 你敢交給代理初審、哪些你這輩子都要人類簽字？那條分界線該畫在哪、憑什麼畫在那？

**🎒 今日帶走：** 2026 下半年 AI coding 的勝負手，不是模型多會寫，而是一群代理在團隊裡「被看見、被指揮、被把關」的方式——而這套「代理自驗、人類簽核」的邏輯，正是半導體驗證與 sign-off 的翻版。
