## 🎯 今天的主軸｜開放網路對 AI agent 升起吊橋：驗不了身分，網路只好一律先擋

今天大多數新聞其實是同一個故事的三個切面：**開放網路正在對 AI agent 關門**，而且不是因為 agent 技術不行，是因為「驗不了身分、又傷到網站的商業模式」。

**共同變化**：擋在前面的是 Cloudflare（它擋在全網約五分之一流量前面）：它現在把「頁面上有廣告」直接當成「這頁是做給人看的」訊號，**預設就擋掉 agent 類爬蟲**、拒絕 AI 訓練爬蟲、只放行搜尋引擎。背景數字很嚇人——光是 AI 訓練爬蟲，到今年 6 月已佔整體爬蟲請求的 52%（2025 春天還只有 22%）。同時，一支失控的 AI agent 艦隊被抓到在野外繞過封鎖、謊報身分；「網站封鎖 agent 害合法自動化斷掉」的災情本週也開始見報。

**為什麼放在一起看**：它們是同一條因果鏈——網站有動機擋（廣告養不活、爬蟲暴量），agent 有原罪（驗不了、還會偽裝），於是倒楣的是使用者：合法的比價、研究、採購 agent 一起被掃進門外。網路分不清誰是好 agent、誰是壞 agent，最省事就是「全部當可疑份子」。

**過去 vs. 現在**：過去開放網路預設「門是開的」，robots.txt 是一紙君子協定（爬蟲自己宣告、自己自律）；現在預設整個翻過來——門預設是關的，而且不再相信 agent 自報的 User-Agent 字串（那行字誰都能亂寫），改在網路層用「驗證過的 bot 身分＋IP 範圍」比對。從「信任自律」走到「預設不信任」，是開放網路少見的立場翻轉。

**背後邏輯（內容經濟學）**：Cloudflare 官方部落格講得很白：「一個 agent 會讀價格、讀評論，卻永遠不會看那則廣告。」網站靠人類眼球看廣告賺錢，agent 把內容吸走卻不帶收入，等於白吃。於是 Cloudflare 把單一的「擋 AI」開關拆成搜尋／訓練／agent 三個獨立控制，並推 Pay-Per-Crawl 讓內容方收「過路費」。這已不只是資安，而是「誰該付錢養內容」的根本之爭。

**對你的工作**：如果團隊有流程「悄悄靠 agent 自動抓外部資料」（競品價格、法規、datasheet、IP 授權頁、供應鏈行情），這些流程會開始變脆；當內容開始收過路費，agent 的「每任務成本」要多算一筆「內容通行費」，改變你評估自動化划不划算的算式。

**限制與待驗證**：Cloudflare 的預設封鎖目前主要套用在新網域、免費層、有廣告的頁面，既有付費客戶維持原設定；零售商品頁反而歡迎 agent（AI 來的流量轉換率高 3–5 倍）。失控艦隊「自稱是 Claude」只是指紋比對的推論（編輯分析：指紋指向中國混元／GLM，Anthropic 並未被證實涉入）。Web Bot Auth 的標準化進度各家說法不一，尚待 IETF 塵埃落定。

**記住這句**：開放網路正在長出「免疫系統」——它分不清好壞 agent，於是先把所有 agent 當可疑份子，而通往下一個時代的門票，叫做「可驗證的身分」。

> 👤 延伸解讀（官方部落格觀點）：Cloudflare 那句「我們把『頁面上有廣告』當成這頁是做給人看的訊號」，等於把一個哲學問題變成技術規則——網路要先假設內容是為人而寫，agent 想進來就得先證明自己不是來白吃的。這是把「開放」重新定義成「對可驗證者開放」。

### Web Bot Auth：給 agent 發一本「網路護照」

既然「全部擋光」會傷到好 agent，業界正推一條活路：Web Bot Auth。它用 RFC 9421 HTTP 訊息簽章，讓 agent 用自己掌握的私鑰替每個請求簽名；operator 把公鑰放在固定的 well-known 網址，網站收到請求後讀 Signature-Agent 標頭、抓公鑰、離線驗章即可放行。Cloudflare 的驗證 bot 計畫與 AWS WAF 都已導入，IETF 也在推標準化。

> 💡 記住這句：擋光所有 agent 不是終點，建一條「驗證過的快速通道」才是——未來你的 agent 可能要先辦證才上得了路。

🔗 [閱讀原文](https://developers.cloudflare.com/bots/reference/bot-verification/web-bot-auth/) ｜ 來源：Cloudflare Developers ／ IETF Internet-Draft

### Cloudflare 把「擋 AI」拆成三個開關——關鍵是誰付錢

這波封鎖的底層邏輯是內容經濟學，不是單純資安。Cloudflare 把原本一個「擋 AI bot」的開關，拆成搜尋引擎、訓練爬蟲、agent 三類分別控管：搜尋照放（能帶流量）、訓練預設拒絕、agent 在有廣告頁預設擋。它同時主打 Pay-Per-Crawl 讓內容方自動定價收費。（例外：零售商品頁多半不受影響，因為 AI 帶來的訪客轉換率高出傳統搜尋 3–5 倍。）

> 💡 記住這句：開放網路的下一戰，是把「免費抓取」變成「按次計費」——內容正在從公共財變成有價商品。

## 📖 今日概念｜可驗證的機器人身分（Verified Bots）與簽章式請求

**定義**：讓一支自動化程式用密碼學「簽名」證明自己是誰，而不是靠一句隨便就能亂寫的自我介紹（User-Agent 字串）。

**生活化比喻**：User-Agent 就像你自己用印表機印的名牌，上面寫「我是 Claude」——誰都能印一張；簽章式請求則像護照裡的防偽晶片，驗的人拿「發照機構的公開名冊」一刷，馬上知道真假。

**工作中的例子**：網站收到請求 → 讀 Signature-Agent 標頭 → 去該 agent 公布的 well-known 網址抓公鑰 → 用 RFC 9421 驗簽 → 驗過才放行；全程可離線快取，不必每次打電話問對方。

**常見誤解**：「只要擋掉 User-Agent 帶 bot 字樣的就安全」——錯。壞 agent 會偽裝成一般瀏覽器（本期那支失控艦隊正是如此），真正要驗的不是它「說」自己是誰，而是它「能不能證明握有某把私鑰」。

**與今天主軸的關係**：主軸的死結是「驗不了身分，只能一律先擋」；可驗證身分就是想解開這個結——讓好 agent 有條活路，壞 agent 無所遁形。

## 🏭 半導體 AI 專區｜設計空間最佳化（DSO）——用 RL 自動搜「工具的上百個旋鈕」

**分類：** EDA 工具
**內容屬性：** 背景知識

**問題與流程位置**：從 RTL 到 GDS，合成與實作工具有成百上千個參數旋鈕（綜合策略、佈局密度、時序約束權重、擁塞設定……）。過去靠資深工程師憑經驗一輪輪手調，一次跑好幾天；搜尋空間大到沒人能窮舉，好配方常是碰運氣碰到的。這件事卡在數位實作流程（synthesis → place → route → signoff）的「配方搜尋」環節。

**AI 如何介入**：DSO（Design Space Optimization，代表工具 Synopsys DSO.ai／Cadence Cerebrus）把它變成強化學習問題：把 PPA（效能／功耗／面積）當獎勵，讓 RL 自己調旋鈕、看結果、再調，一輪輪收斂到好配方。和過去最大的差別是——過去是「人猜方向、機器執行」，現在是「機器自己探索方向」，把原本幾週的 PPA 探索壓到幾小時，還會跑出人類不會想到的旋鈕組合。（注意：這是 RL 搜參數，跟近期熱門的「LLM 代理跑簽核流程」是不同路線，別混為一談。）

**資料與產出**：輸入是設計網表＋約束＋工具旗標空間；產出是一組「配方」（工具設定）與對應的 PPA 結果。以下數字皆為廠商或客戶宣稱、非獨立驗證：Synopsys 稱 DSO.ai 可帶來約 3 倍生產力、功耗最多降 25%、面積明顯縮小；SK hynix 曾述某專案 cell 面積減 15%、die 縮 5%；Cadence 在某 12nm CPU 案例稱線延遲改善 83%、漏電降 17%，從零訓練約 50–200 次迭代即可收斂。

**如何驗證**：DSO 給的是「候選配方」，不是免簽核的答案——產出仍要跑完整的 timing／power／DRC／LVS 簽核才算數。這恰恰呼應今天主軸：機器會給你一個看似漂亮的結果，但你得自己把關驗證。

**限制與風險**：數字多為特定專案宣稱，不同設計與製程節點差異極大；RL 需要可觀算力與工具授權成本；搜出的配方可能對設計微調很敏感（過擬合某個 corner）；它不會取代工程師對架構與約束的判斷。

> 👷 對半導體工作者的意義：實體設計／CAD 團隊最直接受惠——把「調旗標」的苦工交給機器，人力移去「定目標、設約束、把關簽核」。可嘗試的下一步：在非關鍵 block 上小規模導入 DSO，把它當「探索器」而非「決策者」，先建立對它輸出的驗證節奏。
