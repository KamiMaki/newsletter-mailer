## 🎯 今天的主軸｜AI 代理開始「按產業裝箱出貨」——賣的不再是一顆模型，而是寫好 SOP、接好系統、留好簽核點的工作包；下一道考題是對到損益表

**共同變化**

這兩天最值得看的 agent 新聞，不是誰又刷新分數，而是「把 agent 按產業與職務裝箱」。Anthropic 11/12 推出 **Claude for Manufacturing**：一個外掛（plugin）裡裝了 **17 個技能**（skill，可想成寫成檔案、AI 照著做的 SOP）和 **4 個連接器**（Autodesk Fusion、Infor、Microsoft 365、Oracle NetSuite），涵蓋報價、品質調查、生產報表、故障診斷、採購與設計比較。

🔗 [閱讀原文](https://claude.com/resources/articles/claude-for-manufacturing) ｜ 來源：Claude（Anthropic 官方）

Databricks 11/11 則把 **Genie** 改造成「常駐」的企業同事：可以排程、或在某個指標下跌時被觸發，長時間追蹤任務，缺資料會主動追問；哪些動作能自己做、哪些要你簽，由你設定。同一天 Google 開源部落格說明，它把 MCP 工具和 Agent Skills 綁成 **Agent Plugins** 發行，下一步要標準化技能的打包、搜尋與版本管理。

🔗 [閱讀原文](https://www.databricks.com/blog/new-genie-autonomous-ai-complex-enterprise-work) ｜ 來源：Databricks Blog

🔗 [閱讀原文](https://opensource.googleblog.com/2026/11/scaling-ai-agents-open-standards-mcp-aaif.html) ｜ 來源：Google Open Source Blog

**為什麼放在一起看**

打個比方：過去 AI 廠商賣的是**食材**（模型），你得自己想菜色、備料、掌火候；現在開始賣**調理包**——附菜譜（技能檔）、配好料（連接器接進 ERP、設計工具）、還標明「出餐前請主廚試吃」（人工簽核）。說回技術：三家其實在包同一件事的三層——Anthropic 包**產業流程**、Databricks 包**長時間執行與治理**、Google 包**發行格式**。

第四則新聞是這股風潮的鏡子。Genpact 11/12 公布對 2,000 多位營收 10 億美元以上企業高管的調查：**79%** 已有 agent 上線，但只有 20% 廣泛且一致地使用，**15%** 完整把 AI 投資連到損益，過去兩年資助的 AI 專案平均 49% 達到預期價值（皆為自報）。調理包要解決的，正是「試過了」到「天天用、算得出錢」之間那段距離。

🔗 [閱讀原文](https://www.prnewswire.com/news-releases/79-of-enterprises-report-ai-agents-in-production-but-only-15-have-fully-tied-ai-investment-to-pl-outcomes-302937385.html) ｜ 來源：Genpact 新聞稿（PR Newswire）

**過去 vs. 現在**

**過去**：給你一個聊天框，提示詞、資料匯出、格式整理全靠自己，每個工程師一套私房 prompt，換人就失傳。**現在**：廠商先把「品質工程師處理一次檢驗不合格」寫成流程——記錄失效、翻過去同類報告、排出可能原因、起草矯正措施報告——並綁好要讀哪個系統、最後由誰放行。安裝後對 Claude 說一句「Set us up」，它會先測試連接器，回報哪些技能還跑不完整。

**背後邏輯**

模型能力逐漸趨同、價格往下掉（同一天 Google 的 Hydrogen 打出每百萬 token $1.50／$7.50），差異化只能往上走：**懂你的流程、接得上你的系統、過得了你的稽核**。治理因此被做成產品功能——Claude for Manufacturing 明說**不操作設備、不寫入記錄系統**，在 Infor 的權限跟著使用者走，要改單得另裝 Infor 自家外掛並經採購核准；Genie 以使用者身分行動、每個動作可追溯，管理者可設預算與核准規則。

編輯分析：這是用「唯讀＋起草＋人簽核」換企業 IT 點頭。先拿文書工作立功，再談碰到真正的系統。

> 👤 延伸解讀：Google Cloud 工程師、MCP 核心維護者 Kurtis Van Gent 在官方開源部落格表示，他接下來的重心是 Agent Skills 的打包、發現與版本管理。換句話說，「技能檔」正在變成要像軟體套件一樣管理的資產。

**對你的工作**

對半導體廠的品保、設備、廠務與 IT：最先被改變的不是機台控制，而是**機台周邊的文書**——異常單、矯正措施報告、交班報告、供應商詢價。可以做的下一步：挑一個「每週重複、輸入來自既有系統匯出、輸出最後有人簽核」的流程，把資深同事腦中的判斷寫成步驟明確的 SOP（這就是技能檔的雛形），先用唯讀資料試跑，追兩個數字：**起草時間**和**簽核退件率**。

**限制與待驗證**

- Claude for Manufacturing 只具名 6 個技能、沒有客戶案例或效益數字；連接器以 ERP 與設計工具為主，半導體廠常見的 MES、FDC、良率系統都不在清單，沒連接器的系統得靠定期匯出到 Microsoft 365。
- Genie 宣稱任務正確率 91%、是較強前沿 agent 的 1.6 倍，用的是 Databricks 與 Turing 合建的基準，屬廠商自報。Genpact 數字同樣是問卷自報。
- 裝箱帶來新的鎖定：技能檔、連接器與治理設定都綁在單一平台。技能打包標準化仍在進行，跨平台能否真的帶著走，尚待驗證。

**記住這句**

模型會變成大宗食材，值錢的是寫成技能檔的「你家 SOP」——AI 代理開始帶著產業流程與簽核點出貨，但能不能對到損益，還得你自己對帳。

## 📖 今日概念｜記錄系統（System of Record, SoR）

**定義**：某一類資料「以它為準」的權威系統，例如 ERP 的訂單、MES 的批次履歷、設備保養系統的維修紀錄。

**生活化比喻**：銀行帳戶 vs. 你的記帳 App。App 可以分析、提醒、幫你寫月報，但錢到底在哪裡，以銀行帳為準。說回技術：AI 代理就像那個記帳 App，能讀、能分析、能起草，但真正「算數」的改動必須寫回記錄系統，並經過權限與簽核。

**工作中的例子**：在晶圓廠，lot 的履歷在 MES、機台狀態與保養在設備管理系統。AI 起草異常報告時可以讀這些資料；但 hold／release 一批貨、關閉一張維修單，必須由有權限的人寫回 MES 才算生效。

**常見誤解**：「AI 讀得到就等於能改」，或「AI 產生的報告就是紀錄」。前者是權限問題，後者是流程問題——草稿沒經簽核、沒寫回記錄系統，就只是草稿。

**與今天主軸的關係**：今天的產業工作包，邊界幾乎都畫在記錄系統前面：Claude for Manufacturing 明說不寫入記錄系統，Genie 以使用者身分、依原系統權限行動。看懂這條線，就看懂了企業為什麼敢讓 agent 進門。

## 🏭 半導體 AI 專區｜設備預測維護（Predictive Maintenance）：從「按時間換件」到「看健康度換件」

**分類：** IC 製造

**內容屬性：** 背景知識（另引一則今日新聞事實）

**問題與流程位置**

機台突然停機，在製晶圓可能報廢、產線排程全亂。傳統只有兩條路：**壞了再修**，或**定期保養**（按時間、片數換零件，常把還能用的零件提早換掉）。預測維護位在設備工程與廠務之間，要回答的是：這台機台**什麼時候該保養**最划算。

**AI 如何介入**

過去靠工程師看管制圖、憑經驗訂保養週期。經典研究是 Susto 等人 2015 年發表於 IEEE TII 的論文：以離子佈植機鎢燈絲斷裂為對象，訓練多個**不同預測時間窗**的分類器，再用「意外停機成本 vs. 零件剩餘壽命浪費」的成本函數決定何時保養——AI 把「何時換」變成可以計算的取捨。Siemens 2026 年 8 月的技術部落格描述較新的做法：先學每台設備健康時的**運轉指紋**（電流、振動、溫度、壓力，蝕刻機另有 OES 光譜與 RF 阻抗），偏離就告警並連到可能原因；示範中再讓 LLM 讀保養程序與設備資料，摘要變化、建議檢查項目。

🔗 [閱讀原文](https://doi.org/10.1109/TII.2014.2349359) ｜ 來源：IEEE TII（Susto et al., 2015）

🔗 [閱讀原文](https://blogs.sw.siemens.com/electronics-semiconductors/2026/08/13/ai-driven-predictive-maintenance-solving-semiconductor-fab-uptime-challenges/) ｜ 來源：Siemens 技術部落格（2026/8）

今日新聞事實：Claude for Manufacturing 的故障診斷技能，同樣是讀感測匯出、維修紀錄、照片與手冊，排出可能原因交給技術員確認——LLM 正從「預測」補上「解釋與排查」這一段。

**資料與產出**

輸入：FDC 感測時序、零件更換與維修紀錄（失效標籤的來源）、RF 小時與片數計數器；Siemens 描述單台蝕刻機每天可產生 10–50 GB。產出：異常分數與告警、「未來 N 批內失效機率」、可能原因排序與建議檢查項目。

**如何驗證**

用歷史保養週期回測：提前多久預警、誤報率（叫你停機其實沒事）與漏報率；以成本函數比較預測維護與定期保養；上線先跑影子模式——只告警、不改排程。

**限制與風險**

故障樣本稀少（Susto 論文的基準案例只有 33 個保養週期、3,671 批）；改機、腔體濕洗後指紋會漂移；誤報一多，工程師就會開始忽略告警。Siemens 文中「停機最多降 30%、提前 20–40 分鐘預警」為範例目標而非實測，不能當成果引用。（編輯分析）

> 👷 對半導體工作者的意義：設備工程師與廠務的第一步，不是挑模型，而是盤點保養紀錄是否結構化、能否和 FDC 時間戳對齊——沒有乾淨的失效標籤，預測維護只能停在異常偵測；LLM 適合先放在「讀手冊與維修紀錄、排可能原因」的輔助位置，由人決定是否停機。

## 🪞 反思時間

- 如果把你部門最常寫的一份報告（例如矯正措施報告或交班報告）交給 agent 起草，你得先把哪些「只存在資深同事腦中」的判斷寫成步驟？這份技能檔又該由誰維護、多久更新？
- Genpact 說 79% 企業有 agent 上線，只有 15% 連到損益。在你的團隊，該用哪個指標證明一個 agent 值得續約：省下的工時、簽核退件率，還是停機時間與良率？
- 當技能檔、連接器和治理設定都綁在某一家平台上，三年後要換供應商時，哪些資產是你帶得走的？現在該怎麼保存它們？

**🎒 今日帶走：**模型是食材，SOP 才是菜譜——AI 代理開始帶著產業流程出貨，但最後的簽核與對帳仍在你手上。
