## 🎯 今天的主軸｜Agent 的上線考題換了：不是「它會不會做」，而是「它代表誰、能開哪幾扇門」

**共同變化**

想像你請了一位代辦員，幫你跑銀行、郵局和公司檔案室。他能力再好，真正讓你睡不著的問題是：他手上拿的是誰的授權書？每扇門都用同一張萬能卡，還是到哪扇門才拿哪把鑰匙？過去 48 小時，Google、阿里雲、GitHub 不約而同在處理同一件事：把 agent 的「授權書」從一張萬能卡，拆成跟著「使用者本人」走、按工具逐一發放、而且全程有人看的權限管線。

**為什麼放在一起看**

11/20 這天，Google 前線部署工程師 Neeraj Agrawal 連發兩篇實作文。第一篇講企業自己做 agent 介面、直接呼叫 Gemini Enterprise 的 StreamAssist API 時，必須自己扛起三層認證：

- 誰在問：員工用 Google 帳號，或用 Entra ID／Okta 登入後，到 Google STS 換一張短效 token；只有不分人的後台機器人，才用工作負載身分。
- 連接器授權：每位員工對 Drive、SharePoint、Jira 各授權一次，refresh token 存在託管的 Keystore。
- 逐工具授權：自訂 ADK agent 的受保護工具被呼叫時，才跳出同意視窗。

第二篇講把企業內網的 MCP 伺服器接給 agent：每次工具呼叫要過兩道身分檢查，一個 header 驗「是不是 Gemini Enterprise 這個服務在叫」，另一個 header 帶「使用者本人的 OAuth token」。

同一天，阿里雲用「一個閘道、一把 API 金鑰、資料列級安全（RLS）寫在資料庫裡」收斂 agent 的資料存取。三篇放在一起看，答案都是：服務身分和使用者身分要分開，兩個都要驗。

🔗 [閱讀原文](https://developers.googleblog.com/how-to-handle-user-connector-and-agent-auth-in-gemini-enterprise-with-a-custom-ui/) ｜ 來源：Google Developers Blog（自訂 UI 的三層認證）

🔗 [閱讀原文](https://developers.googleblog.com/how-to-securely-connect-internal-cloud-run-mcp-servers-to-gemini-enterprise/) ｜ 來源：Google Developers Blog（私有 MCP 伺服器連線）

🔗 [閱讀原文](https://www.alibabacloud.com/blog/with-postgresql-firmly-in-place-as-the-data-foundation-what-else-do-agents-need-to-truly-run_603796) ｜ 來源：Alibaba Cloud Blog

**過去 vs. 現在**

過去：做聊天機器人最省事的做法，是開一個服務帳號，給它讀全部資料的權限，誰來問都用它去查。現在：Google 的文章直接點名這是錯誤用法。如果拿「工作負載身分」去處理個人化資料，系統會把所有請求都當成同一個身分，逐人的文件存取控制（ACL）就整個失效，實習生問得到只有處長能看的檔案。反方向的錯誤也被點出來：把 OAuth 設在 agent 根層，使用者在問任何問題前，就得先把所有連接系統登入一輪。正解是「用到哪個工具，才拿那把鑰匙」。

**背後邏輯**

回到代辦員的比喻：門禁卡證明「這人是物業派來的」，對應服務身分；住戶簽的授權書證明「他代表 302 室」，對應使用者 token。兩張缺一張，門都不該開。技術上，這就是委派授權（delegated authorization）：agent 不擁有權限，它只是暫時借用使用者的權限，而且只借到這次任務需要的範圍。Google 的私有 MCP 做法把這件事落實到 header 層級：X-Serverless-Authorization 由 Cloud Run IAM 驗完就剝掉，Authorization: Bearer 則交給 MCP 應用自己驗。網路也一起收緊：DNS 只覆寫該 MCP 服務的精確主機名稱。文中提醒，若覆寫整個 *.run.app，可能劫持同一共享 VPC 內其他服務的名稱解析。（編輯分析）商業邏輯很直白：企業採購 agent 的最後一關不是準確率，而是資安稽核。誰能把權限管線講清楚，誰就能過關。

**對你的工作**

如果你在 IT／數位轉型單位規劃內部 agent，例如查 MES 批次紀錄、良率報表、設計文件庫，第一份設計文件該寫的是身分流，不是 prompt：哪些查詢必須帶工程師本人的身分？哪些只是不分人的公開查詢？跨客戶的產品資料靠什麼隔開？（編輯分析）在晶圓廠與 IC 設計公司，「同一個資料庫裡放著 A 客戶和 B 客戶的產品」是常態。用共用服務帳號去查，等於讓 agent 成為繞過 need-to-know 原則的後門。

**限制與待驗證**

這三篇都是廠商教學與架構文，綁定各自的產品（Gemini Enterprise、Agent Gateway、阿里雲 RDS），換平台就要重做。Google 私有 MCP 那篇沒有談效能、成本與故障處理；阿里雲提到的 AGE 圖查詢「100 倍」是廠商自報，沒有獨立驗證。更根本的問題還沒解：委派授權只保證 agent「不會越權」，不保證它「在權限內不亂來」。後者得靠行為監測，而那還在私人預覽階段。

> 👤 人物觀點／延伸解讀：Google 前線部署工程師 Neeraj Agrawal 在文中點出分水嶺：只要應用程式改用自訂介面、直接呼叫 StreamAssist API，原本內建網頁幫你做好的登入、ACL 與連接器授權，責任就轉到客戶自己的前後端身上。（延伸解讀：「自己做介面」的隱藏成本，就是自己扛身分。）

**記住這句**

agent 不該有自己的萬能卡。它該拿著「你」的授權書，到哪扇門才拿哪把鑰匙，而且門口要有人看。

## 📖 今日概念｜三方 OAuth（3-Legged OAuth）與委派授權

**定義：** 由「資源擁有者（你）」親自同意，讓「第三方應用（agent）」在限定範圍內代你存取「資源伺服器（例如 SharePoint）」的授權流程；應用拿到的是有期限、有範圍的 token，不是你的密碼。

**生活化比喻：** 飯店房卡。櫃檯確認你是房客後，發一張只開 1205 房、退房日就失效的卡。你把卡借給送洗衣服的服務生，他能進你的房間，但開不了隔壁房，也拿不到你的身分證。對應到技術：房卡就是 access token，「只開 1205」就是 scope，「退房失效」就是到期時間。

**工作中的例子：** 你讓內部 agent 讀 Jira 工單。第一次使用時會跳出 Jira 的同意視窗，你按下允許，agent 之後就用你的身分查工單：你看得到的它才看得到，你看不到的專案它也碰不到。

**常見誤解：** 「有 OAuth 就安全了。」OAuth 只確保 agent 拿到的是你的權限、而不是更多；如果你本人的權限本來就開得太大，或 agent 在權限內做了蠢事（例如刪錯工單），OAuth 一樣攔不住。所以還需要最小權限和行為監測。

**與今天主軸的關係：** Google 文中的第二層「Federated Connectors（3LO）」就是三方 OAuth；第三層「逐工具授權」則是把同意的時機延後到真正用到工具的那一刻。

## 🏭 半導體 AI 專區｜Chiplet 配對最佳化：讓「有瑕疵但可修」的晶粒湊成能用的系統

**分類：** IC 製造（先進封裝）

**內容屬性：** 背景知識（近期論文，arXiv 2611.19544，11/14 投稿）

**問題與流程位置**

一顆 chiplet 系統由多顆晶粒透過 die-to-die（D2D）介面接在一起。每條介面有多條 lane，也預留了少量備援 lane。晶粒測試後常見的狀況是：某幾條 lane 壞了，但用備援可以修。麻煩在於，能不能修取決於「它跟誰配對」：A 晶粒壞左邊的 lane、B 晶粒壞右邊的 lane，兩顆配在一起，備援可能不夠用；換個搭檔卻剛好都能修。這一步發生在晶圓測試之後、組裝之前的晶粒分配（die matching）環節。

**AI 如何介入**

過去：常見做法是只用通過測試的晶粒（known-good die），或依分級（bin）粗略配對，可修但有瑕疵的晶粒容易被報廢。現在：亞利桑那州立大學與 Ampere Computing 的 DT-MATCH 把配對寫成最佳化問題，同時考慮 lane 級缺陷位置、備援數量與結構相容規則，目標是讓能正常運作的 SoC 數量最大化。它提供兩種解法：整數線性規劃（ILP）搭配分批近似，解的品質較好；GRASP（貪婪隨機自適應搜尋）快得多，但不保證最佳。兩者共用一段前處理來縮小問題規模。（編輯分析）這裡的「AI」是廣義的最佳化與搜尋，不是深度學習；它的價值在於把原本靠經驗分配的流程，變成可以計算、可以比較的決策。

**資料與產出**

輸入是每顆晶粒的 lane 級測試結果（哪幾條壞、備援剩多少）和系統拓撲規則；產出是「哪顆配哪顆」的組裝清單，以及預估可組成的良品數。

**如何驗證**

論文在工業設計上比較兩種方法：ILP 品質較佳，GRASP 執行時間較短、品質相近。摘要沒有公布良率提升百分比或執行時間的具體數字，要看全文才能確認。導入產線前，應以歷史批次回測：同一批晶粒，用新配對法和現行規則各算一次良品數，並追蹤組裝後的最終測試結果。

**限制與風險**

這是研究成果，不代表已在任何產線量產落地。配對最佳化有個前提：晶粒的測試資料必須準確，而且能追溯到每一顆晶粒。此外，配對結果會影響晶圓庫存、批次排程和出貨順序，最佳解在物流上不一定可行。

🔗 [閱讀原文](https://arxiv.org/abs/2611.19544) ｜ 來源：arXiv（DT-MATCH，ASU／Ampere）

> 👷 對半導體工作者的意義：負責先進封裝良率、測試與 MES 整合的工程師，可以先盤點一件事：我們的 lane 級測試資料有沒有保存，並能追溯到每顆晶粒？有了這份資料，「報廢還是配對」才有被最佳化的空間。
