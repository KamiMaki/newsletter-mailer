## 🎯 今天的主軸｜雲端從「少量大批」改成「多樣少量」：OS、資料庫、防火牆開始照 agent 的作息改尺寸

**共同變化**
感恩節週末的新聞不多，但有三則不起眼的更新剛好拼出同一張圖：雲端業者不再只是「讓 agent 也能跑」，而是把 agent 當成主要工作負載，回頭改作業系統、資料庫和資安的預設尺寸。一則改 Linux 的記憶體管理，一則改資料庫的計費與啟停單位，一則改防火牆的偵測邏輯——三層都在回答同一個問題：當主要客人從「長時間跑的人類服務」變成「成千上萬個短命、忽大忽小的 agent」，底層該長什麼樣？

**為什麼放在一起看**
用晶圓廠的語言最好懂。傳統網站服務像少量大批的成熟製程：同一批貨一路跑到底，機台參數調一次就穩。agent 工作負載則像多樣少量加急單的研發線：每張單要的東西不一樣、隨時插進來、做完就走，換線成本與等待時間反而成了主角。三則消息分別在三個工站處理換線問題。

**① 作業系統：記憶體要能「切碎了也好用」。** 阿里雲 11/27 介紹 Alibaba Cloud Linux 4 時點名 agent 負載的特徵：反覆開子程序、直譯器記憶體一直配置又釋放、跑編譯和測試；每個沙箱配額固定，實際用量卻隨工具呼叫起伏，高併發時少數慢實例就會拖住整批。解法是自適應多尺寸大頁（mTHP）：連續記憶體夠就用大頁，不夠就逐級退到中等大小。在 192 核主機塞滿 96 個 2 核 2GB 沙箱的合成測試中，對比預設設定的 Ubuntu 24.04，批次完成時間 136.2 秒→121.6 秒（−10.71%），主機記憶體峰值 41.15 GB→32.26 GB（−21.60%）。
🔗 [閱讀原文](https://www.alibabacloud.com/blog/agent-tasks-10-71%25-faster-memory-footprint-21-60%25-lower-%7C-introducing-alibaba-cloud-linux-4_603827) ｜ 來源：阿里雲官方部落格

**② 資料庫：計費單位從「一套系統」變成「一個任務」。** AWS 11/27 推出 Amazon Neptune Graph Sessions，官方形容為「為 agent 設計的運算模式」：每個 agent、使用者或任務都能有自己的一張圖，不必付佈建型圖資料庫 16 m-NCU 的最低門檻；起始 4 或 8 個 s-NCU，可長到兩倍，閒置 15 分鐘縮到零、資料保留，下一個查詢來時數秒內恢復，按實際用到的記憶體計費。
🔗 [閱讀原文](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-neptune-graph-sessions-generally-available) ｜ 來源：AWS What's New

**③ 資安：攻擊者也換成 agent 了。** 同一天阿里雲宣布正式推出 Agentic WAF。文章指出 AI 攻擊者會看伺服器回應改編碼、換入口、被擋就除錯重試，還會把一次攻擊拆成多個請求。架構分兩層：線上串接的小模型即時判斷可疑請求；旁路 AI 引擎以 IP 為起點串起連續嘗試、重建攻擊鏈，再把繞過手法回灌偵測規則。文中引用「高風險漏洞年增 314%、利用時間中位數從 8 小時降到 22 秒」，但未註明數據出處，也沒有公布偵測率或誤擋率。
🔗 [閱讀原文](https://www.alibabacloud.com/blog/your-waf-is-being-bypassed-how-to-handle-continuous-mutated-attacks-from-ai-agents_603824) ｜ 來源：阿里雲官方部落格

**過去 vs. 現在**
過去：底層為「少數長壽服務」最佳化——開一台資料庫給整個應用、作業系統假設程序穩定、防火牆假設攻擊者照固定腳本。現在：底層開始為「大量短命、彼此隔離、用量忽大忽小」的 agent 調尺寸——隔離單位變小、閒置成本趨近零、偵測對象從單一請求變成一串會學習的嘗試。

**背後邏輯**
商業面：同週阿里雲公布 AI 雲端營收年增 53%，客人在變，貨架就得跟著改。技術面是密度經濟——一個 agent 的價值可能只有幾分錢，要划算只能在同一台機器塞更多沙箱、讓閒置資源不收錢。編輯分析：這也是為什麼記憶體（而不是 CPU）先被改：沙箱一多，誰的記憶體碎片拖慢誰，就決定了整批的尾端延遲。

**對你的工作**
如果你的 IT 或 CAD 團隊正在規劃內部 agent 平台，評估重點要從「單一 agent 跑得多快」改成三個量產問題：一台主機能穩定塞幾個沙箱、最慢的那幾個拖多久；每個任務的資料能否獨立建立、閒置時不付錢；資安是否假設對手也是會自動試錯的 agent。EDA 授權與運算農場本來就熟悉「排隊與利用率」，這套語言可以直接搬過來。

**限制與待驗證**
Alinux 4 的主要數字來自合成測試，對照組核心版本不同（6.8 vs. 6.6），無法把效益全歸功於 mTHP；記憶體省下來也不等於能多開同規格機器。Neptune 縮到零後「數秒恢復」沒有更精確數字。Agentic WAF 沒有任何偵測成效數據，引用的攻擊統計也無出處。三則都是單一廠商自述，尚待第三方實測。

> 👤 延伸解讀（編輯分析）：這條線和 11/25 AWS 執行長 Matt Garman 專文主張「agent 需要獨立身分類型與基礎設施層隔離」同方向但不同層次：當時談身分與隔離，今天看到的是隔離之後的密度與成本——隔得越細，底層就越要為「很多小房間」而不是「幾棟大樓」設計。

**記住這句**
agent 讓雲端從量產線變成研發線：贏家是換線最快、閒置最便宜、而且預設對手也會自己試錯的那一家。

## 📖 今日概念｜吵鬧的鄰居（Noisy Neighbor）

**定義：** 多個租戶共用同一台實體機器時，某一個租戶突然大量使用記憶體、快取、磁碟或網路，拖慢其他租戶效能的現象。

**生活化比喻：** 像公寓共用一條水管：隔壁同時開洗衣機和淋浴，你家的水壓就掉了。換回技術：每個沙箱有自己的 CPU 配額，但記憶體頻寬、快取與實體記憶體碎片是共用的，這就是那條水管。

**工作中的例子：** EDA 運算農場上，一個大型實體設計工作吃滿記憶體頻寬，同機的模擬回歸就一起變慢；今天的 Alinux 4 文章也提到，刻意製造記憶體碎片化時，未最佳化版本的 p99 執行時間會升到原本三倍以上。

**常見誤解：** 「有配額就有隔離」。配額只限制你能用多少，不保證共用資源不被擠壓；看平均值也會漏掉問題，吵鬧鄰居的傷害主要出現在尾端延遲（p95／p99）。

**與今天主軸的關係：** agent 讓一台主機上的鄰居從幾個變成幾十個，而且每個都忽大忽小。改作業系統記憶體管理、把資料庫切成每任務一張小圖，本質上都是在處理越來越多的吵鬧鄰居。

## 🏭 半導體 AI 專區｜ATPG 測試向量生成：從「搜尋加回溯」到「梯度下降」

**分類：** IC 設計（DFT）

**內容屬性：** 背景知識

**問題與流程位置：** 晶片出廠前要在測試機上灌入一組輸入向量，抓出製造缺陷。ATPG（自動測試向量生成）就是在 DFT 階段產生這組向量的工具。痛點是大部分向量其實是為了少數「難偵測故障」而生，向量越多，測試機時間越長、每顆晶片測試成本越高。傳統 ATPG 用 D 演算法、PODEM 這類搜尋法，逐一設定輸入、走不通就回溯，難故障上常耗在大量回溯。

**AI 如何介入：** 一是把離散題目變連續題目：Wei Li、Shawn Blanton 等作者的 DEFT（arXiv 2512.23746，2026/5 更新至 v3）把每個輸入位元改成可微分的機率值，用重新參數化讓連續目標對齊實際故障偵測，再用梯度下降直接推出向量，並以自訂 CUDA 核心與梯度正規化在深電路上穩定訓練。過去是一步一步試、錯了退回；現在是同時調整所有輸入、沿梯度往「抓得到故障」的方向走。二是讓 AI 指揮傳統搜尋：InF-ATPG（arXiv 2512.00079）把電路切成無扇出區域，用圖神經網路表示電路，再以強化學習決定搜尋方向。

**資料與產出：** 輸入是閘級網表與故障清單（如 stuck-at 故障）；產出是測試向量集。DEFT 也支援部分指定向量：只指定必要的 0/1 位元，其餘留給壓縮器填。

**如何驗證：** 對比一套領先商用工具，DEFT 向量數平均少 27.3%、最多少 75.9%；部分指定模式下 0/1 位元少 19.3%、偵測到的故障多 35%。InF-ATPG 回溯次數比傳統方法平均少 55.06%、比先前 ML 方法少 38.31%。向量是否真的偵測到聲稱的故障，可由故障模擬器逐一確認。

**限制與風險：** 兩篇皆為預印本，摘要未列具體基準電路，商用工具也未具名；DEFT 作者定位為補充既有 ATPG 啟發式而非取代。編輯分析：實務上更可能先專攻難偵測故障，與既有壓縮架構、時序感知測試、低功耗測試限制的整合仍待驗證。

🔗 [DEFT（arXiv 2512.23746）](https://arxiv.org/abs/2512.23746) ｜ [InF-ATPG（arXiv 2512.00079）](https://arxiv.org/abs/2512.00079)

> 👷 對半導體工作者的意義：DFT 與測試工程師可以先盤點「哪些故障吃掉最多向量」，那就是 AI 型 ATPG 最可能先發揮的地方；向量數直接換算測試機秒數，是少數能清楚算出 ROI 的 AI 應用。

## 🪞 反思時間

- 如果你們內部的 agent 數量一年內成長十倍，現有的運算農場或雲端架構，最先撐不住的會是 CPU、記憶體、授權數，還是資安監控？你怎麼知道？
- 「縮到零、按用量計費」讓每個任務都能有專屬資源，但也讓成本難預測。在你的部門，你會怎麼設計預算與上限，讓工程師敢用又不失控？
- 當攻擊者是會自己試錯的 agent，靠人工判讀告警的防守節奏還來得及嗎？晶圓廠或設計中心的哪些系統最需要先換成「自動串攻擊鏈」的防禦思維？

**🎒 今日帶走：** agent 把雲端從量產線變成研發線——底層比的是換線速度、閒置成本，和防得住會自己變招的對手。
