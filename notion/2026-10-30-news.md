## 🎯 今天的主軸｜寫程式變便宜了，卡關的是「誰來審、誰來合」——agent 起草過四成 PR，GitHub 同日補上審查與合併的自動化

**共同變化**

想像一條產線突然多裝了十台機台，品檢站卻還是一個人——產量越高，品檢站越塞。今天 GitHub Universe 的一整串發布，講的就是這件事：據 Octoverse（[TNW 轉述](https://thenextweb.com/news/github-universe-copilot-fusion-octoverse-agents)），9 月已有**超過 40% 的 PR 由 agent 起草**，3 月只有 17%；單月 1.1 億個。GitHub 自己說這是下限，因為並非每個 agent 都偵測得到。技術意義：「寫」的成本掉下去之後，人類的注意力成為稀缺資源，工具開始往「審」和「合」的環節補人手。

**為什麼放在一起看**

單看每一則都像普通功能更新，合起來是一條線：**Code Review Max**讓多個審查 agent（跨不同模型供應商）各自獨立看一遍，再由彙整 agent 合成一份審查；**Copilot 核准**正式 GA，核准可計入必要核准數；**Agent Merge**在 PR 上按「Watch and fix」，Copilot 會在雲端開發環境替你修壞掉的 Actions 與合併衝突，並可接 auto-merge；**Automations**則能依「建議被接受或被拒絕」的結果，提出修改自己 prompt 的提案。[Code Review Max／核准](https://github.blog/changelog/2026-10-28-copilot-code-review-merge-with-confidence-with-max-and-approvals) ｜ [Agent Merge](https://github.blog/changelog/2026-10-28-agent-merge-watches-and-fixes-pull-requests-in-the-cloud) ｜ [Automations](https://github.blog/changelog/2026-10-28-copilot-automations-now-learn-from-outcomes-and-self-improve)

**過去 vs. 現在**

過去：人寫、人審、人修 CI、人解衝突，每一步都吃人的時間。現在：agent 起草、另一批 agent 審、再一個 agent 盯著 PR 修到能合——人退到「決定哪些路徑可以讓 AI 核准、哪些一定要人看」。

**背後邏輯**

兩個邏輯並行。第一是**經濟面**：生成幾乎免費，審查是新的成本中心，所以廠商把審查也產品化、並用 AI 額度計價（Max 比 Lite、Balanced 慢且耗更多額度）。第二是**控制面**：核准預設關閉、管理員可限定 Copilot 能核准的檔案路徑、新的 push 會讓舊核准失效、Automations 的自我改進必須經人接受才生效——全都是在「讓 agent 多做」與「別失控」之間畫線。

**對你的工作**

即使你不在軟體公司，EDA 腳本、PDK 工具鏈、Fab 內部資料管線、驗證環境都在用 Git。當 agent 開始大量送 PR，值得先決定：哪些目錄（例如 sign-off 腳本、約束檔、製程參數）禁止 AI 核准、必須人審？CI 要不要鎖定 Actions 依賴（見下方衍生新聞）？

**限制與待驗證**

① 40% 是「起草」而非「合併」，TNW 轉述的內容沒有給出 agent PR 的合併率或缺陷率；② Max 的 ReviewBench 最高 F1 是 GitHub 自己的說法；③ 編輯分析：多個審查 agent 若出自相近訓練資料，容易犯同樣的錯，「多重保險」可能沒有想像中保險（見今日概念）；④ Max 價格未公開，只說耗費較多 AI 額度。

> 👤 **延伸解讀（編輯分析）**：這次最值得注意的不是任何單一功能，而是「審查」被拆成可設定的等級（Lite／Balanced／Max）與可設定的權限（路徑級核准）。這代表審查正從一種人的習慣，變成可以被調度的資源，就像機台產能。

**重點一句話**

**AI 讓「產出」變便宜，下一個戰場是讓「可信的驗證」也變便宜——而且要知道哪些地方不能便宜。**

## 📖 今日概念｜相關性失誤（Correlated Errors）

**一句定義：**相關性失誤（Correlated Errors）：多個審查者「同時犯同一種錯」的傾向；如果錯誤高度相關，找十個審查者不比找一個安全多少。

**生活化比喻：**像請五位同一所學校、同一位老師教出來的人來校稿——他們對同一個專有名詞會一起看漏。人數多不等於視角多。

**工作中的例子：**用同一個模型寫 RTL、再用同一個模型寫 testbench，兩邊會共享同樣的規格誤解，驗證通過卻不代表設計對；因此驗證常要求獨立團隊、獨立方法（形式驗證 + 模擬）。

**常見誤解：**「多開幾個 agent 審就更安全」——只有在它們的盲點不同（不同模型、不同資料、不同方法）時才成立。Max 強調跨供應商模型，正是在處理這點，但實際獨立程度仍待驗證。

**與今天主軸的關係：**審查被自動化後，真正要問的是：這些審查者之間夠不夠獨立？這決定了「全自動核准」可以放到哪一層。

## 🏭 半導體 AI 專區｜微影熱點（Lithography Hotspot）偵測：先快篩、再精確模擬

**分類：** EDA 工具

**內容屬性：** 背景知識

**問題與流程位置**

【背景知識】晶片的版圖就算通過設計規則檢查（DRC），到了微影這關仍可能印不出來或良率偏低，這類位置叫「微影熱點」。它出現在實體驗證與早期實體設計階段。完整微影模擬很準，但要掃整顆晶片太慢，也很難放進佈局迭代裡。

**AI 如何介入**

【背景知識】Gao、Yu、Pan 的綜述指出，圖樣比對與機器學習可以更快地篩出熱點，品質足以用於全晶片實體驗證與設計。**過去**：整顆晶片跑詳細模擬，或靠人工整理規則；**現在**：先用快速模型把可疑區域篩出，再只對少數候選送去精確模擬確認，並可在佈局階段就避開，而不是等簽核才發現。

**資料與產出**

輸入是版圖圖樣，標籤通常來自微影模擬或晶圓檢測結果；產出是熱點位置與風險分數，供設計師修改版圖或後續工具使用。（以上為論文摘要所述方向，細節以原文為準。）

**如何驗證**

快篩模型的結果要回到精確模擬或實測校驗：漏掉的熱點（漏報）比多報更致命，所以評估要看召回率與新圖樣上的泛化。

**限制與風險**

【編輯分析】這是 2013 年發表的背景綜述，不是今日新聞，也不代表任何特定公司的量產流程；不同製程節點與微影條件的圖樣分布不同，模型換節點需重新驗證。我們沒有可靠的公開數據說明產線上的改善幅度，因此不作量化宣稱。

🔗 [Gao, Yu, Pan：Lithography Hotspot Detection and Mitigation in Nanometer VLSI（arXiv:1402.3150）](https://arxiv.org/abs/1402.3150)

> 👷 對半導體工作者的意義：實體驗證與 DFM 工程師可以檢視自己流程中「哪一步靠全量模擬、哪一步可用快篩模型先擋」——但篩選模型的漏報率要被獨立驗證，這和今天 agent 審查的邏輯一模一樣。

## 🪞 反思時間

- 如果你的團隊明天開始收到大量 AI 起草的 PR 或腳本變更，你會把「哪些路徑必須人審」寫在哪裡？由誰決定、多久重審一次？
- 你目前的驗證流程中，有哪些「審查者」其實是同一個來源、同一種方法？要加什麼獨立性才算真的多一層保險？
- 如果 AI 讓「產出」的速度再快十倍，你的工作流程裡第一個塞住的環節會是哪裡？現在就能做什麼來鬆開它？

**🎒 今日帶走：**寫的成本在掉，審的成本變成新的產能；誰能把「可信的驗證」做得又快又獨立，誰就握住下一輪的槓桿。
