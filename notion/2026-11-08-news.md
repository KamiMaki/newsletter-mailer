## 🎯 今天的主軸｜agent 的表現不只看模型，更看它「讀到的環境」——程式庫與知識庫的衛生，正變成要維運的資產

**共同變化**
新同事第一天翻抽屜，看到一張寫著「這個 bug 要修」的便利貼就動手，卻沒人告訴他那張貼了三年、早就修好了。今天幾則消息指向同一件事：agent 會把讀到的東西當作該做的事，所以它讀到的環境乾不乾淨，直接決定效率與正確性。

**為什麼放在一起看**
Google 量化「髒環境」的代價；阿里雲 Kitta 示範「乾淨、專屬的知識」怎麼蒸餾出來；阿里雲的 15 個 agent 研發小隊強調架構知識要持續維護；GitHub 讓審查意見的引用來源（skills、MCP、自訂指令）能被 API 查到。從清掃、蒸餾到稽核，是同一條知識供應鏈的三個環節。

> 👤 Google「Agent Distraction」（11/6）：分析數千名工程師的 agent 追蹤紀錄（數億步驟），以帶 bug 編號的 TODO／FIXME 為代理訊號，與 bug 即時狀態和使用者提示交叉比對。約 13% session 接觸到這類註解；agent 在 94% 情況忽略、6% 會針對該 bug 動作，其中 83% 非使用者要求；這些繞路中 41% 指向已修好或作廢的票，每個 session 多出 70% 步驟、77% token、105% 等待時間。Google 用 agent 掃描並提刪除，半年清掉數千筆過期引用，人工通過率超過 95%。限制：未點名模型，為 Google 內部資料的觀測迴歸。
🔗 [閱讀原文](https://developers.googleblog.com/agent-distraction/) ｜ 來源：Google Developers Blog

**過去 vs. 現在**
過去，過期註解只是人類讀者的小雜訊，清不清都沒差，所以清理專案常年排不上。現在，agent 一個 session 讀成百上千個檔案，而且不會憑直覺分辨新舊；文章建議重新評估這些被擱置的清理工作。

**背後邏輯**
Kitta 不靠通用模型「看感覺」審 patch，而是把真實審查與缺陷紀錄清洗成「判斷準則」與「帶標準答案的驗證樣本」，再以 workflow（去哪看）與 knowledge（怎麼判）客製。阿里雲的 15 agent 小隊文章指出：典型功能開發約 20 個工作天只有約 2 天在寫程式，寫碼加速 10 倍也只省到約 18.2 天，瓶頸是架構約束與經驗能否被收集、更新。GitHub 則從管理面補一塊：能查到審查意見引用了哪些 skills、MCP、自訂指令，並在企業、組織、儲存庫三層管理設定。

> 👤 延伸解讀（編輯分析）：舊的 lint 守護程式碼風格，新的環境 lint 守護「agent 會讀到什麼」。這是編輯的推論，不是各家官方的共同說法。

**對你的工作**
（編輯分析）半導體團隊的 RTL 倉庫、SDC 約束、waiver 清單與流程腳本裡，滿是「TODO: ECO 後再放寬」「此違規暫時 waive」這類備忘。agent 讀到它們，可能把已失效的備忘當成當前需求。下一步：先用腳本找出指向已結案單號的註解，列入每季清理；再為 agent 另寫一份「現行有效」的短規範。

**限制與待驗證**
Google 的數字來自單一公司、單一類型註解，不代表所有過期文件；Kitta 與 15 agent 小隊成果均為廠商自報，尚無獨立評測，且依賴昂貴的專家整理；Kitta 自研 PR 意見採納率僅 41.8%、準確度 73.6%。GitHub 更新是管理能力，並未證明審查品質提升。

**記住這句**
換更強的模型之前，先把 agent 每天翻的那個抽屜整理乾淨。

## 📖 今日概念｜過期上下文（Stale Context）與上下文衛生

**定義：** 提供給模型的資料中，已經失效卻仍看似有效的內容（舊註解、舊文件、舊規則），會被模型當成當前事實或任務。

**生活化比喻：** 過期的交接手冊——新人照著做，操作的卻是三年前已拆掉的設備。模型沒有「這頁很舊」的直覺，只能靠內容與日期線索。

**工作中的例子：** 驗證環境的 README 還寫著要跑舊版 testbench，agent 照著跑了半天；或腳本裡「TODO: 等 ECO 後移除此 waive」已無人記得。

**常見誤解：** 「上下文愈多愈好」。Google 的資料顯示，多讀到的過期備忘會讓繞路增加；資料要新、要可追溯，比多更重要。

**與今天主軸的關係：** 主軸談的清掃、蒸餾與稽核，都是在管理過期上下文。

## 🏭 半導體 AI 專區｜良率偏移的根因追查：設備共同性分析

**分類：** IC 製造
**內容屬性：** 背景知識（來源為 2024 年 Semiconductor Engineering 報導與 INFORMS WSC 論文；48 小時內未找到可靠的半導體 AI 新聞）

**問題與流程位置**
良率偏移（excursion）指多批 lot 突然、非預期地良率偏低，成因常在製造中未被管制，多半到晶圓功能測試才發現。第一步通常是設備共同性分析：把低良率 lot 的製程履歷攤開，找出共同經過的機台或製程步驟。Semiconductor Engineering 引述 Onto Innovation，共同性分析與 ANOVA 是典型第一步。🔗 [Semiconductor Engineering](https://semiengineering.com/yield-management-embraces-expanding-role)

**AI 如何介入**
過去靠人工挑變數、逐一做 ANOVA；步驟數成百上千時，兇手可能是「某兩台機的組合」，貪婪式搜尋容易漏掉。WSC 論文用 Gibbs sampler 找「有問題的機台組合」，以機率抽樣取代窮舉。另有專利描述用機器學習先篩選相關情境資料，減輕資料量拖慢分析的問題（編輯註：專利內容，不代表已大規模量產）。🔗 [INFORMS WSC 論文](https://www.informs-sim.org/wsc12papers/includes/files/inv222.pdf)

**資料與產出**
輸入：lot／晶圓的設備履歷、wafer map、FDC 與量測資料。產出：嫌疑機台／機台組合排名與信心程度。

**如何驗證**
以已知根因的歷史偏移回測；再用機台維修或換件後的良率變化做前瞻驗證。

**限制與風險**
相關不等於因果；資料散在多系統、需要整合；機台間樣本量不均會誤導排名。

> 👷 對半導體工作者的意義：良率與製程整合工程師可先檢查自家偏移分析是否只看單機台，並確認設備履歷與 wafer map 能在同一處即時取得——AI 再強，也得吃得到乾淨的履歷。

## 🪞 反思時間

- 如果 agent 每天讀你的 RTL 倉庫、約束檔與 waiver，你能立刻說出哪幾個檔案裡的備忘其實已失效嗎？誰該負責清理，又該如何定期檢查？
- Kitta 把專家審查經驗蒸餾成知識庫，而自研 PR 的採納率只有 41.8%。放到你的簽核或驗證流程，哪一類判斷已有足夠的「標準答案樣本」，哪一類還沒有？
- 當 agent 的引用來源（skills、MCP、自訂指令）能被稽核時，你的團隊會把哪些內部知識放進去、又不願意放哪些？理由是什麼？
