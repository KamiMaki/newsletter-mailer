## 🎯 今天的主軸｜AI 做設計的產出單位，從「一次性的答案」變成「可重用、可批量驗證的積木」

**共同變化**　這週有四個互不相識的團隊，做出了同一個決定：**不讓 LLM 直接交出最終成品**，而是讓它在一個「別人已經驗證過的積木盒」裡組裝，並且配一個又快又便宜的裁判。類比版圖那篇（arXiv 2610.38426）發現，直接叫模型畫幾何圖形，瓶頸主要是時間與 token 成本；改成讓它修改 gLayout 這類**生成器框架**的程式，因為底層是驗證過的基本元件（primitive），每次修改小、好檢查。

**為什麼放在一起看**　它們的共通點是「**誰在把關**」：①類比版圖——驗證過的 primitive 加上「在最容易出錯的家族成員上測試每次修改」；②RNGD NPU kernel 迴圈（arXiv 2610.38329）——12 天內為 Gemma-4-12B 的三個 decode kernel 找到最佳化，先用便宜的檢查篩掉設計、才上真實裝置，幾何平均比官方基準快 **9.293 倍**，且每個 kernel 距離「光搬權重所需週期」不到 1.25 倍；③RISC-V CPU（arXiv 2610.39570）——LLM agent 在人類監督下，把單週期 RV32I 核心演進成三發射亂序 RV32IM，**用 FPGA 板上量測取代 RTL 模擬**，8,000 次 CoreMark 迭代比單執行緒 RTL 模擬快 9.6 倍，還抓到一個短測試看起來更好、跑久了效能衰退的候選；④Alibaba 的 Sentinel（見衍生新聞）——agent 沒有 shell，只能呼叫 195 個預先定義的鑑識工具。

**過去 vs. 現在**　過去的 AI 輔助設計像請廚師「現場做一道菜」，好不好吃要等你嚐；現在更像給廚師一整櫃**預先調好的醬料（積木）**，並在旁邊放一個試吃員（評估器）。**輸出不再是一張圖或一段程式，而是一個可被反覆執行、批量檢驗的「生成器」。**

**背後邏輯**　成本結構在改變：探索很貴（token、機台時間、人的審查），但**一旦修改被驗證，就能套到整個家族**——類比版圖論文提到，參數化生成器讓一次編輯可同時評估多個變體，且這些家族測試結果還能拿來訓練較小的本地模型，用低很多的推論成本學會「對整個家族都成立的修改」。NPU 那篇也有類似的經濟學：便宜檢查先擋掉壞設計，貴的裝置實測只留給少數候選，晚期因為讀數有雜訊，還得反覆和最佳版本比對。

**對你的工作**　半導體團隊其實早有這套文化：PCell、標準單元庫、sign-off 規則——都是「被驗證過的積木」。新的是 agent 可以**動手改積木的組合邏輯**。實務上值得做的是：盤點你的流程裡哪些是「已驗證 primitive」、哪些有「便宜裁判」（快速 DRC、FPGA 原型、輕量時序估算），這些地方最適合先放 agent。

**限制與待驗證**　三篇都是**研究成果／案例**，不是量產流程：類比版圖的實驗在 SKY130 開源製程上，與先進節點的複雜度、LVS／寄生考量仍有距離；RISC-V 實驗是在人類監督下完成，規模是一顆小核心；NPU 案例是單一晶片、競賽的第一輪。另一個隱憂是「裁判本身會不會被 agent 鑽漏洞」——FPGA 量測與 CoreMark 並不等於你的真實工作負載。

**重點一句話**　**想讓 agent 可靠，別先問它多聰明，先問它手上的積木有沒有被驗證、旁邊的裁判夠不夠快。**

> 👤 延伸解讀（編輯分析）：三篇論文都是預印本與單一案例，結論要打折看；但它們指向同一個可檢驗的假設：瓶頸正從「模型會不會做」移到「驗證做不做得起」。

## 📖 今日概念｜知識蒸餾（Knowledge Distillation）

**定義**　讓一個大模型（老師）把它「會的判斷」教給一個小模型（學生），小模型學的是老師的輸出，而不只是原始標準答案。

**比喻**　像資深工程師帶新人：新人不需要重修十年經驗，只要大量看資深者在各種情境下怎麼下判斷，就能在日常案子上做到八九成，而且薪水便宜很多。重點是：學生學的是「老師的做法」，不是把老師整個複製過來。

**工作中的例子**　類比版圖論文提到，在整個版圖家族上驗證過的修改結果，可以當作監督訊號去訓練較小的本地模型。放到你的工作：用大模型在內部程式庫上產生並驗證過的修補，來訓練一個能放在公司內網、不外送設計資料的小模型。

**常見誤解**　常見誤解是「蒸餾 = 壓縮到一樣好」。實際上學生通常只在老師示範過的範圍內表現好，遇到沒見過的情境會掉得比老師快；而且老師的錯誤也會被一併學走。

**與主軸的關係**　今天的主軸說的是「驗證過的結果可以反覆利用」，蒸餾就是把這份驗證成本攤到更便宜的模型上。

## 🏭 半導體 AI 專區｜類比版圖生成器：讓 LLM 改『生成器程式』而不是畫圖

**分類：** IC 設計

**內容屬性：** 背景知識（含 10/28 近期預印本，非 48 小時內新聞）

**問題與流程位置**　**【背景知識】**類比版圖（運算放大器、比較器等）至今大多靠人手畫，因為匹配、對稱、寄生與設計規則互相牽制。業界常見的緩解方式是 PCell／參數化生成器：用程式描述一個「版圖家族」，改參數就產生不同尺寸的版本。問題是撰寫生成器本身仍需要資深工程師。

**AI 如何介入**　**【近期研究，arXiv 2610.38426】**作者在開源製程 SKY130 的 gLayout 框架上做受控實驗，比較三種作法：讓 LLM 寫生成器、直接畫版圖幾何、或在既有生成器框架內工作。結論是直接畫的瓶頸主要在時間與 token 成本；在框架內工作則能重用驗證過的 primitive，使每次修改很小、容易檢查。**與過去的差異：**以前一次人工修改只影響一張版圖；現在對生成器的一處修改可以同時評估整個家族。

**資料與產出**　輸入是生成器原始碼與設計規則；產出是修改後的生成器，以及它在多個家族成員上產生的版圖。

**如何驗證**　論文建議把測試集中在「最可能失敗的家族成員」上；驗證依賴框架內建的設計規則感知與 primitive 的既有驗證。家族測試結果還可用來訓練較小的本地模型。

**限制與風險**　**【編輯分析】**實驗是在開源製程上，尚不等於先進節點的 DRC／LVS／寄生簽核；論文未顯示取代人工版圖工程師的量產成果。真正落地還需把公司內部 PDK 規則與簽核工具納入同一個迴圈。

🔗 [閱讀原文](https://arxiv.org/abs/2610.38426) ｜ 來源：arXiv 2610.38426

> 👷 對半導體工作者的意義：類比／混合訊號版圖工程師、PCell 開發者與 CAD 團隊：值得試的下一步，是挑一個你們最常改的 PCell，盤點它有沒有「快速可跑的規則檢查」，再評估讓 LLM 提改動、由檢查把關的可行性。

## 🪞 反思時間

- 你的流程裡，哪些步驟已經有「被驗證過的積木」和「夠快的裁判」？如果現在放 agent 進去，它的產出會被什麼擋下？
