🎯 今天的主軸

agent 的運行單位，正從「一次呼叫」變成「一個 session」——能續跑、能追蹤、能算帳，才是長跑 agent 的新基本功

▍共同變化

想像一輛長途貨車。以前的 AI 應用像短程快遞：一通電話、一次回覆，掛了重打就好。現在 agent 像跨省貨運——要開幾個小時、停靠很多站（呼叫模型、用工具、寄信、改檔案），所以需要三樣東西：拋錨能從上一站接續（續跑）、有行車紀錄器（追蹤）、按趟計油耗（計費）。11/5–11/6 阿里雲的三篇官方文章剛好各補一塊：Durable Agent 講續跑，SLS SessionStore 講追蹤，AI Gateway 的 FinOps 講計費。

▍為什麼放在一起看

三件事共用同一個前提：系統得先承認「session」是一等公民。Durable Agent 文章把它講得很清楚：session recovery 只是還原對話脈絡，durable 則要讓「任務執行」本身不中斷。它的做法是把進度、呼叫意圖與結果存在行程之外，用原子提交（tool 結果、回執、任務完成一起寫入）與分階段 checkpoint，重啟時從「該階段開頭」重來，而不是從崩潰的那一行。SLS 把模型呼叫、工具呼叫、步驟等 OpenTelemetry 資料重組成 trajectory／session／feature 三種視圖；AI Gateway 則把用量拆成 Session→Turn→Model Call，列出 token、cache 命中率、工具呼叫數、首 token 延遲。續跑要有 session 才知道「接哪裡」，追蹤要有 session 才知道「查哪趟」，計費要有 session 才知道「這趟花多少」。🔗 Durable Agent・SLS・AI Gateway

▍過去 vs. 現在

過去：以「請求」為單位——每次呼叫獨立計費、獨立記錄，掛了就整段重跑（連已付費的 token 一起浪費）。現在：以「任務」為單位——狀態外置、事件可重建、成本可歸因到某個 agent、某個 turn。Microsoft Learn 的 Durable Task 文件（2026/5 版，屬背景）也用同樣的語言：agent 可能跑「數小時到數週」，崩潰後若無恢復機制，得重新消耗已花掉的 token。

▍背後邏輯

這是把後端工程的老功夫（工作流引擎、冪等、分散式追蹤）搬給 agent。其中最微妙的是「結果不確定的動作」：Durable Agent 文章舉例——要寄 5 封通知信，前 3 封已確認、第 4 封不確定有沒有寄出、第 5 封還沒開始。系統不能盲目重播，而是把第 4 封標成「interrupted」，靠工具宣告能否安全重播、外部系統提供冪等鍵或查詢能力來確認。商業面上，計費拆到 turn 層級也有明確動機：企業終於能看出是哪個 agent、哪個步驟燒掉 token，再回頭改模型、上下文或工具流程。

👤 延伸解讀（編輯分析）

Restate 等廠商部落格主張「單靠 checkpoint 不等於生產級的 durable execution」，因為 agent 的工具會有寄信、付款、部署等副作用。這是廠商立場，但與阿里雲文章強調的「不確定動作需冪等鍵」互相印證。來源為第三方部落格，僅作觀點參考，不當事實依據。

▍對你的工作

若你的團隊在跑 EDA 腳本代理、回歸測試分流或良率分析 agent（一跑就是數小時），評估平台時多問三題：中斷後從哪裡接？一次失敗能不能還原成完整軌跡？這次任務花了多少 token、卡在哪一步？這三題的答案，比再多 2% 的基準分數更決定它能不能進入正式流程。

▍限制與待驗證

① 三篇都是阿里雲自家產品文章，缺獨立第三方的可靠度數據，也無價格或效能基準；② 續跑能保證「狀態不丟」，不保證「外部副作用只發生一次」，後者仍取決於每個外部系統是否支援冪等；③ 追蹤資料本身含 prompt 與工具輸出，存放與權限是新的治理議題（編輯分析）。

agent 真正上線的門檻不是更聰明，而是「中斷後能接、出事能查、花費能算」——先把 session 當成一等公民。

📖 今日概念｜Trace 與 Span（追蹤樹）

一句定義｜Trace 是「一件任務從頭到尾的完整紀錄」，由許多 span（一步操作的起訖時間、結果與附註）組成的樹。

生活化比喻｜像快遞追蹤單：整張單是 trace，每個站點（收件、轉運、派送）是一個 span，點進去看得到何時進站、停多久、有無異常。

工作中的例子｜一個 agent session 是一棵 trace：底下有 turn，turn 底下有 model call 與 tool call。AI Gateway 的 Session→Turn→Model Call 下鑽，就是這種樹；SLS SessionStore 支援的 OpenTelemetry traces，則是業界通用格式。EDA 流程裡，一次回歸測試分流的每一步也可以這樣被記錄。

常見誤解｜① trace 不等於 log：log 是散落的句子，trace 把它們串成因果；② 有 trace 不代表能「重播」——要能安全重播，還要冪等與狀態外置；③ trace 會含 prompt 與工具輸出，需要權限控管。

與今天主軸的關係｜續跑、追蹤、計費三件事，都靠「把一個 session 切成可辨識的步驟」才能成立；trace／span 正是這個切法。

今日新聞（研究論文）＋背景

▍問題與流程位置

高階合成（HLS）讓設計者用 C/C++ 描述演算法，再由工具合成 RTL。LLM 能從自然語言規格直接產生 HLS-C，但難點在後面：要同時通過解析、編譯、測試平台（TB）與合成，多輪工具回饋常被浪費——同一個錯反覆修、修好 A 又弄壞 B。屬於 IC 設計前段的 RTL／HLS 產出環節。

▍AI 如何介入

【今日新聞：研究論文】arXiv 2611.07324（11/5 提交，MementoHLS）提出雙記憶引導的修復：一份「可執行修復合約庫」把跨任務的 HLS 知識變成需有證據才放行的修復動作；另一份「審查者背書的證偽帳本」記錄本任務哪些修法無效、哪些進展已驗證，避免重蹈覆轍。Same-Candidate Reviewer 把解析、編譯、TB、合成結果綁在同一個候選上，Single-Commit Arbiter 每輪最多提交一個候選。對比過去：以前是人看報錯、憑經驗逐項改；現在是把「經驗」與「失敗史」寫成機器可查的帳本，讓每一輪修復有依據。

▍資料與產出

輸入為自然語言規格與工具回饋；產出為可合成的 HLS-C。論文報告：HLS-Eval（94 題）同候選 TB∧Synth 的 pass@1 由 41.7% 升至 58.9%、pass@5 由 57.4% 升至 68.1%；Bench4HLS（170 題）pass@1 由 15.5% 升至 32.4%、pass@5 由 32.9% 升至 50.6%（以上為作者在公開基準上的自述結果，我只讀了摘要）。

▍如何驗證

關鍵設計是「同一個候選」必須同時通過測試平台與合成，避免「測試過的是 A、合成的是 B」的假進步。

▍限制與風險

【編輯分析】基準題多為小型模組，與工業級 IP 的規模、時序與面積壓力仍有距離；通過 TB 與可合成不等於 PPA 達標；論文尚屬研究成果，不能視為已在產線導入。
