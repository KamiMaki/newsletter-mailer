🎯 今天的主軸

最強模型的賣點，從「答得多好」變成「能交出多少機器可核對的保證」：會出錯的 AI 外面，正被套上一層不會出錯的檢查器

▍共同變化

想像兩個學生交數學作業。第一個只寫答案，老師得自己重算一遍；第二個附上每一步推導，而且格式嚴謹到閱卷機能逐行自動核對，老師只要確認「題目抄對了沒」。昨天（11/10）有三則新聞指向同一件事：AI 正從第一個學生變成第二個。換成技術語言：讓機率式的模型負責「生成」，讓確定性的工具負責「判對錯」，人類則退到上游去審規格。

▍為什麼放在一起看

① AlphaProof Code：Google DeepMind 的多模型代理框架。人類專家先和模型一起把 Signal 協定的安全目標寫成形式化規格，並逐條審過；接著由 Gemini Carbon 驅動的代理用 Lean（一種能讓電腦逐步檢查證明的語言）寫證明。結果是超過 600 萬行 Lean，人工複審約 1%，耗時 4 週，官方說過去要專家團隊花好幾年。證明的對象是裝置上實際執行的編譯後程式碼，不只是協定設計。研究者還把兩個早已修掉的漏洞放回隔離版本，系統兩次都產出「這版不安全」的機器可檢證明。

② Gemini 4 Carbon 全面開放（🔄 後續追蹤：10 月底僅限資安計畫試用）：Google 直接說它比 Argon「用更多 token 去探索、推理更久、跑更長的驗證迴圈」。在 Antigravity 的 /swarm 多代理模式裡，Carbon 負責架構、協調與稽核，較輕的模型做平行苦工。資安方面主打找漏洞、利用、修補一條龍，並產出「已驗證的根因修補」。定價：11/30 前每百萬 token 輸入 2 美元、輸出 10 美元，之後調成 4 美元與 20 美元。

③ NVIDIA 把 OpenShell 捐給 CNCF：這是一個開源 runtime，對 agent 的工具呼叫、推論服務存取與工作負載執行套上確定性政策，現為 CNCF Sandbox 專案。它不證明程式正確，而是保證「不管模型怎麼想，越界的動作一律擋下」，和 ①② 是同一套思路。
🔗 閱讀原文｜來源：NVIDIA Blog（11/10，KubeCon）

▍過去 vs. 現在

過去：形式化驗證被稱為「最高等級的安全保證」，但因為寫證明太貴，只用在作業系統核心、航太等極少數地方。AI 寫程式時，大家靠測試與人工 code review 把關，速度卡在「人看得完多少」。現在：最貴的那一步（寫證明）交給模型，判對錯交給 Lean 這類核對器，人力集中在規格與 1% 的旗標區。瓶頸從「寫得出來嗎」移到「規格寫對了嗎」。

▍背後邏輯

產品邏輯很直接：當各家模型的分數越來越接近，「可以少審多少」就比「多答對幾題」更能換成錢。商業上，Carbon 的單價是 Argon 的兩倍（優惠期後），而且刻意多花 token 做驗證，意思是 Google 賭企業願意為「保證」付較高價格，而不是只買更快的答案。（編輯分析）技術上，這套分工能成立的前提是存在一個便宜、確定且可信的裁判：Lean 核心、編譯器、政策引擎都是。哪個領域有這種裁判，AI 就能在那裡放手跑。

▍對你的工作

開發者與工程主管可以先盤點：團隊裡哪些環節已經有「確定性裁判」，例如型別檢查、單元測試、LEC、DRC、政策檢查？這些地方最適合讓 agent 長時間無人值守地跑。沒有裁判的環節，先投資建裁判，而不是換更強的模型。（編輯分析）對 IC 團隊來說這不是新觀念：等價性檢查、model checking、sign-off 規則本來就是「生成器外面包檢查器」。新的地方在於，軟體世界現在也開始用這套方法來收 AI 的作業。

▍限制與待驗證

第一，證明只保證「符合規格」。規格漏寫的性質，證明再長也蓋不到，所以 AlphaProof Code 才要人類逐條審規格。第二，「1% 人工複審」「4 週」是 Google 自報，獨立團隊還沒驗證；目前開源的是驗證成果，框架本身是否開放並未說明。第三，反例來自同一天的 Gemini Robotics 2.5：機器人在物理世界沒有 Lean 可以核對，只能拿 200 多項任務的測試與 96% 的試點成功率說話。有裁判的領域走向「證明」，沒裁判的領域仍然只能靠「統計」，兩者不能混為一談。

📖 今日概念｜可信計算基（Trusted Computing Base, TCB）

定義

一個系統裡，你「不得不相信它是對的」的最小那一塊。這塊一出錯，整個保證就失效；這塊以外的東西，錯了也會被抓出來。

生活化比喻

超市的電子秤。店員可能手滑、包裝可能貼錯，但只要秤是準的，每筆交易都能被核對。你真正要信任的只有秤，以及秤的校驗章。放到技術上，就是讓 TCB 越小越好、越容易被檢查越好。

工作中的例子

以 AlphaProof Code 來看，600 萬行證明由 AI 寫，不必相信；要相信的是 Lean 的核心檢查器，以及人類逐條審過的規格。（編輯分析）在 IC 驗證中，LEC 簽核時你相信的是等價性檢查工具與參考模型（golden RTL），而不是合成工具本身。

常見誤解

「用了形式化驗證就什麼都不用信」。錯：規格、檢查器、甚至「程式碼如何對應到證明模型」都還在 TCB 裡。另一個誤解是「TCB 越大越安全」，其實相反，要相信的東西越多，可能出錯的地方越多。

與今天主軸的關係

今天的主軸其實是一場「TCB 搬家」：把會出錯的大模型移出 TCB，只留下小而確定的檢查器與人審規格。評估任何「AI 已驗證」的宣稱時，先問一句：這裡我到底還得相信誰？

🏭 半導體 AI 專區｜靜態簽核違規的 ML 分群與根因分析（CDC／低功耗檢查）

▍問題與流程位置

CDC（Clock Domain Crossing，訊號從一個時脈域跨到另一個時脈域）與低功耗（UPF）靜態檢查，是 RTL sign-off 前的確定性裁判。問題是，裁判太盡責了：Synopsys 白皮書指出，十億閘級 SoC 的 CDC 檢查可能吐出上百萬筆違規，每筆在 tape-out 前都得有人看過。真正的設計錯誤往往只有少數幾個，同一個錯會在下游複製出成千上萬筆訊息。

▍AI 如何介入

過去：工程師依模組、依規則逐條篩選，寫 waiver，靠經驗猜哪幾筆是同一個根因。現在：以 Synopsys 的專利 US10586001（2020 年核准）為例，系統先把每筆違規和相關的 debug 欄位配對、補上設計層級的上下文，再轉成數值矩陣，用 k-means、mean-shift 或 BIRCH 分群；接著以結構凝聚度與領域品質分數挑出最佳分群，標出群內變異低的「主導欄位」，並把層級最高的違規標成最可能的根因。等於把「一百萬筆訊息」壓成「幾十個待修的設計問題」。商用工具 VC SpyGlass 的 ML 根因分析，宣稱目標是讓 CDC 除錯與 RTL 簽核快 10 倍（廠商說法，無獨立基準）。

▍資料與產出

輸入是靜態檢查報告（違規類型、時脈或電源域、訊號路徑、debug 欄位），產出是分群結果、每群的根因候選與主導欄位，以及 2D 分群視覺化，讓設計者一次處理一整群。

▍如何驗證

關鍵是 AI 只動「排序與分組」，不動「裁判」。修完根因後重跑 CDC／UPF 檢查，看整群違規有沒有消失。這和今天主軸是同一個邏輯：AI 在外圈加速，確定性工具在內圈判對錯。（編輯分析）

▍限制與風險

分群只是幫忙分流，不是驗證。最大的風險是整群 waive：群裡混進一筆真正的亞穩態（metastability）問題，就會被一起放行，而這類 bug 通常要到矽後才會現形。另外，特徵選擇高度依賴領域知識，換了設計風格可能要重新調整；10 倍加速是廠商說法，尚無公開的獨立數據。
