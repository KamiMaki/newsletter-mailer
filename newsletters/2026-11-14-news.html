🎯 今天的主軸

AI agent 開始「到府服務」：從「把資料送上雲」，變成「把 agent 搬進你的圍牆」

▍共同變化

想像外燴：以前你得把食材（資料）送到餐廳廚房（廠商的雲），菜做好再送回來；現在廚師帶著刀具到你家廚房做菜，食材、刀具、廚房鑰匙都留在你家——只是食譜（模型）多半還在他腦袋裡，必要時打電話回總部問。說回技術：這週三家把 agent 的執行環境、憑證與紀錄搬到客戶自己的邊界裡，模型推論則可另選路線。

▍為什麼放在一起看

四則消息分別處理「agent 住在哪」的不同層：

  • Anthropic（11/12）：Self-hosted Managed Agents 私測，官方原話是「服務的每一部分都跑在你自己的雲或地端」——伺服器、資料庫、沙箱工作機、憑證與對話紀錄都由客戶營運；模型請求可走 Anthropic、Bedrock、Google Agent Platform、Microsoft Foundry 或自家閘道。🔗 來源：Claude
  • GitHub（11/13）：GitHub Copilot app 支援 GitHub Enterprise Server（自架的 GitHub）由預覽轉為正式提供，可直接處理 GHES 上的 repo、issue 與 PR；但雲端 session 不支援 GHES。🔗 來源：GitHub Changelog
  • llama.cpp（11/13）：本地推論引擎的兩個核心函式庫進入 1.0.0，承諾用語意化版本標示 C API／ABI 破壞性變更，支援逾 150 種架構變體——「腦」也能在本地跑的地基，開始有穩定介面可依賴。🔗 來源：Hugging Face Blog
  • AWS（11/13）：Grok 4.7 進入 Kiro 的 AWS GovCloud（US）區域（實驗性支援、500K 脈絡），管理者可控制使用者能選哪些模型——前沿模型搬進受管制的政府雲。🔗 來源：AWS

▍過去 vs. 現在

過去：想用最好的 agent，就得接受它的沙箱、你的程式碼副本、執行紀錄都在廠商那邊；受管制的團隊只能二選一——用雲端最新功能，或守在內網用舊工具。現在：廠商開始把 agent 拆開出貨，你可以只把「腦」留在外面（甚至換成本地開放權重模型），「手」和「帳本」收回家。

▍背後邏輯

（編輯分析）agent 跟聊天機器人最大的差別，是它要動手：跑 shell、讀寫檔案、拿金鑰呼叫內部 API。只要「手」在外面，企業就得把內網的門打開讓它伸進來——這是金融、政府、晶片業遲遲不敢上的主因。Anthropic 同文列出四條不論部署在哪都適用的原則：腦與手分離、憑證不進沙箱、網路只放行白名單主機、每個 session 完整留紀錄（可用 OpenTelemetry 匯出）。換句話說，廠商賣的不再只是模型，而是一套可以拆裝、可以帶進機房的架構。

👤 延伸解讀（官方工程文章）

Anthropic 11/13 的〈Building always-on agents〉把長駐 agent 拆成五個零件：事件收件匣、計時器、記憶、權限（用憑證代理注入金鑰，agent 本身碰不到）、寄件匣。這正好是「自架」時你要接手的清單——每一個零件搬回家，就多一項要自己備份、監控、更新的系統。🔗 來源：Claude

▍對你的工作

IT／資安主管下次評估 agent，問題清單可以從「資料會不會外流」改成三個更具體的問題：腦在哪、手在哪、帳本在哪？各自誰來營運、出事時找誰？工程師則要留意：自架版本常常少了雲端版功能（例如 GHES 沒有雲端 session），選型時要先列出「哪些功能我們真的需要」。

▍限制與待驗證

Anthropic 自架版仍是私測、需透過業務申請，未公布硬體規格與規模建議；即使自架，模型請求仍會離開你的網路（除非走你已簽約的雲端供應商）。反例同樣明顯：DeepSeek 同週把搜尋、讀檔、讀網址全打包進自家 API，AWS 也把雲端 agent 執行環境加速十幾倍——雲端的便利與自架的控制，差距不會自動消失，自架的維運成本與功能落後要算進去。

▍重點一句話

agent 不再是「全有或全無」的雲端服務：把它拆成腦、手、帳本，各自決定放在牆內還是牆外。

📖 今日概念｜共擔責任模型（Shared Responsibility Model）

定義：雲端與 AI 服務中，供應商與客戶各自負責系統的哪幾層安全與維運，用一張清楚的分工表寫下來。

生活化比喻：租房子時，房東管結構、管線、大門鎖芯；你管自己有沒有鎖門、鑰匙借給誰。說回技術：用託管 agent 時，廠商管沙箱、資料庫與修補；改成自架，這幾層就整批移到你這一側。

工作中的例子：公司把 agent 自架在內網後，資料庫備份、沙箱映像檔更新、憑證輪替、紀錄保存期限都要有人簽收；但模型本身的安全訓練與 API 可用性仍由模型供應商負責。

常見誤解：「搬回自家就比較安全。」其實只是責任換人扛——控制權增加，出錯時也沒人可以推。沒有人負責打補丁的自架系統，往往比託管服務更危險。

與今天主軸的關係：腦、手、帳本每搬一塊進牆內，分工表上就有一列從廠商欄移到你的欄。評估自架前，先把這張表寫出來。

🏭 半導體 AI 專區｜LLM 代理自動生成 UVM 驗證平台

EDA 工具 今日新聞（研究論文，作者自報）

▍問題與流程位置

（背景知識）SoC 裡有大量「協定橋接器」，例如把 AHB 匯流排轉成 APB。每做一個新的橋接器，驗證工程師都要手刻一套 UVM 驗證平台（testbench：產生激勵、監看訊號、比對答案的程式），論文估計每個新實例要 40–100 個工程小時。它位於 RTL 完成後、簽核前的功能驗證階段。

▍AI 如何介入

（今日新聞）arXiv 2611.16202（11/12 提交，已獲 ISVLSI 2026 接受）提出一個 Python agent 框架：工程師先寫一份 JSON「驗證清單」，描述介面拓樸、協定語意與覆蓋目標，LLM 據此生成 UVM 平台。關鍵是兩個迴圈：內圈把編譯器錯誤分類後回餵給模型修正，外圈拿覆蓋缺口對照清單、指引下一輪補測。過去流程是「人讀規格→人寫平台→人看覆蓋報告再補」；現在人只寫規格清單，重複的編寫與除錯交給迴圈。

▍資料與產出

輸入是驗證清單與 RTL；產出是完整平台。在 AHB-to-APB 橋接器上，作者自報功能覆蓋率 96.8%、建置速度 4.7 倍，4,623 行生成程式只有 2.1% 需要人工修正，跨四種協定家族加速 3.1–6.1 倍，協定越複雜越划算。

▍如何驗證

以手寫平台為基準比較覆蓋率與工時；生成平台的 scoreboard 還抓到一個手寫基準漏掉的 RTL 功能錯誤。同週另一篇 SVApshot（arXiv 2611.12712）走互補路線：把設計現有行為拍成形式斷言「快照」，用來檢查 AI 之後改 RTL 有沒有改壞。

▍限制與風險

單一作者、主要只在一個設計上完整驗證，頁面未說明使用的模型或是否開源；數字皆為作者自報，尚未見產業導入。（編輯分析）覆蓋率高不代表測對東西——驗證清單寫錯，迴圈只會很有效率地驗證錯的規格。

👷 對半導體工作者的意義：驗證工程師的價值正從「寫平台」移到「寫清楚規格清單、審覆蓋缺口」；可先挑一個重複度高的匯流排橋接器做小規模試驗——而 RTL 與驗證程式碼不能出廠，正好是今天主軸「agent 自架」最直接的用武之地。

🪞 反思時間

  • 如果明天就能把 agent 的「手」和「帳本」搬進公司內網，但「腦」仍在外部雲端，你們的資安規範會把哪些資料畫在「可以送出去」的那一側？理由是什麼？
  • 在你負責的流程裡（設計、驗證、良率、IT），哪一個步驟最常因為「資料不能出廠」而被排除在 AI 工具之外？自架 agent 能解開它，還是真正卡住的其實是別的東西？
  • 雲端版 agent 每季都在變快、變便宜，自架版通常慢半拍。三年後回頭看，你認為受管制產業會走向「全自架」「全上雲」，還是「腦在外、手在內」的混合？什麼訊號會讓你改變判斷？
