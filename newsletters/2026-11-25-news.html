🎯 今天的主軸
agent 不再一顆一顆按按鈕：寫一段小程式，一次把工具用完

想像一位新進工程師在機台前作業：按一個鍵，把讀值抄下來拿給主管看；主管說「再按下一個」，他又跑回機台。一個早上來回二十趟，主管的桌上堆滿了不需要看的中間數字。老手的做法是寫好 recipe，讓機台自己跑完，再把需要判斷的那幾個數字交上去。過去的 AI agent 就像那位新人，每用一次工具，結果就整份送回模型，模型再決定下一步。這週有三家工具同時往「寫 recipe」的方向走。

▍共同變化

agent 呼叫工具的基本單位，從「一次一個工具呼叫」變成「一段會呼叫多個工具的程式」。同時，工具的完整說明書不再一開始就全塞給模型，而是先給目錄、用到才載入。

▍為什麼放在一起看

三家公司、三種產品，卻在同一週調整同一個環節：模型和工具之間的那條線。這不是模型變聰明，而是外層的「工作方式」換了，而且已經從單一工具的實驗，擴散到雲端平台的正式版本路徑上。

▍過去 vs. 現在

過去：要查 50 筆工單、篩出異常、再對每筆異常查細節，agent 得呼叫幾十次工具，每次的原始結果都整份塞回模型的上下文，模型邊讀邊決定下一步。現在：模型寫一段程式，裡面有迴圈、篩選和後續查詢，程式在本機一次跑完，只把最後的摘要交回模型。中間的大量資料從頭到尾沒有經過模型。Anthropic 2025 年 11 月的工程文章舉過一個例子：同一個任務的 token 用量從約 15 萬降到約 2 千。那是單一示範案例，不是通用基準。🔗 背景：Code execution with MCP

▍背後邏輯

兩個原因。第一，每一次來回都要付錢、付時間：模型得重新讀一遍越來越長的上下文，才能決定下一步。第二，程式本來就是模型最熟的語言：迴圈、條件判斷、錯誤處理，用程式表達比用幾十次 JSON 工具呼叫更精準。「按需載入」則解決另一個問題：接了上百個工具，光是說明書就會吃掉一大塊上下文，先給目錄、需要時才翻那一頁就好。

▍對你的工作

如果你正在把 agent 接上內部系統（MES 查詢、良率資料庫、EDA log 解析、license server），工具的設計方式要跟著改：與其開一個「回傳整張表」的大工具，不如提供可程式化組合的小函式，再讓 agent 在沙箱裡自己組裝。對 IT 主管而言，評估 agent 成本時別只看單價，還要看每個任務往返幾次、讀了多少中間資料。

AWS 執行長 Matt Garman 在 11/23 的專文中主張，agent 需要自己的身分類型，權限要在基礎設施層強制限縮，並指出一般容器與主機共用核心，所以 AWS 用 Firecracker 輕量 VM 做硬體級隔離。這是他對產業的主張，不是 Code Mode 的官方規格。但放在今天的脈絡裡正好提醒一件事：agent 一旦開始自己寫程式並執行，執行環境就成了安全的第一線。 🔗 About Amazon

▍限制與待驗證

一、Claude Code 的 Code Mode 仍是實驗、預設關閉，只支援互動式終端機，不支援 VS Code 面板、閘道或雲端工作階段。二、Qoder 的 30%／19% 是自家內部評測，而且只適用於「適合這種做法的情境」。三、程式一次跑完，代表模型看不到中間過程：程式在第 30 筆悄悄出錯時，可能沒人察覺，可觀察性和錯誤回報要另外補上。四、讓模型產生的程式直接執行，沙箱隔離與權限把關變得更關鍵（見衍生新聞）。

▍重點一句話

agent 的效率瓶頸從「模型夠不夠聰明」移到「要來回幾趟」：讓它寫 recipe，而不是一顆一顆按按鈕。

📖 今日概念｜往返成本（Round Trip）與批次化（Batching）

定義：每做一次「送出請求、等回應」都有一筆固定成本，跟這次做了多少事無關；把多件事打包成一次送出，就能把固定成本攤薄，這就是批次化。

生活化比喻：去大賣場買十樣東西，一次推車買齊，和每想到一樣就開車跑一趟，差的不是商品錢，而是九趟的油錢和停車時間。對 LLM agent 來說，「油錢」就是每一輪都要重讀的上下文 token，加上等模型回應的時間。

工作中的例子：ATE 測試採 multi-site 同時測多顆晶粒，爐管一次放一整批晶圓，都是在攤薄裝載、升溫、對位這些固定成本。agent 的 Code Mode 是同一套邏輯：把幾十次工具呼叫寫進一段程式，模型只需要「出門一趟」。

常見誤解：「批次越大越好」。批次越大，單次失敗的代價越高，中間的可觀察性也越差，就像爐管一整批出事，損失比單片大得多。所以批次化通常要搭配中間檢查點與清楚的錯誤回報。

與今天主軸的關係：Code Mode 減的是模型往返的次數，按需載入減的是每趟的行李量。兩者加起來，就是 Qoder 每任務點數 −41% 背後的機制。

🏭 半導體 AI 專區｜LLM 改寫 RTL 時脈閘控：每一刀都要過等價性與功耗檢查
IC 設計 背景知識（近期研究，11/22 上架）
▍問題與流程位置

背景知識：時脈閘控（clock gating）是在暫存器不需要更新時把時脈關掉，省下動態功耗。合成工具會自動插入一部分，但能插多少，取決於 RTL 怎麼寫：條件寫得太粗，工具就找不到可以關的時機。所以在 RTL 階段手動「改寫成好閘控的樣子」一直是功耗工程師的苦工。常用的指標是 flop-gating efficiency（FGE），白話說就是暫存器在不需要更新的週期裡，時脈真的被關掉的比例。

▍AI 如何介入

研究內容：Geuna Chang、Seohyun Kim、Youngsoo Shin 的論文已獲 ASP-DAC 2027 接受。做法是先讓 LLM 產生 Idle、Typical、Peak 三種工作負載，由使用者挑一種當最佳化目標；再由四個 LLM agent 各負責一種時脈閘控技巧，依序改寫 Verilog，專挑 FGE 偏低的暫存器下手。和過去的差別在於：以前是工程師看功耗報告、猜哪裡能改、手改、重跑合成；現在由 agent 大量提案，工程師把關規則。

▍資料與產出

輸入是原始 RTL 和工作負載，產出是改寫後的 Verilog。論文在 5 個 RTL 設計上報告：FGE 平均提升 12.1 個百分點，所選工作負載下的功耗平均降低 23.6%、最高 59.3%；同條件下，某商用工具平均只降 4.1%，純 LLM 基準降 8.6%。

▍如何驗證

關鍵在把關規則：每一次修改都必須同時滿足三個條件才會保留，否則退回。一、功能等價；二、合成後功耗確實下降；三、不違反面積與時序限制。LLM 負責提案，裁判是等價性檢查與合成工具。

▍限制與風險

只測了 5 個設計，商用工具沒有具名；功耗改善是針對「所選的那一種」工作負載，換一種負載未必成立。這是研究成果，沒有任何量產導入的報告。編輯分析：實務上還要考慮閘控單元對時脈樹與 DFT（掃描鏈）的影響，論文摘要沒有涵蓋。

🔗 arXiv 2611.29461（ASP-DAC 2027）

👷 對半導體工作者的意義：低功耗設計與 RTL 工程師最值得試的，不是讓 LLM 直接寫功耗最佳化，而是先把「等價性＋合成後功耗＋時序」做成自動裁判，再讓 agent 在裁判底下大量嘗試。可以從你手上 FGE 最低的幾個模組開始。

🪞 反思時間
  • 當 agent 開始「寫一段程式一次跑完」，中間過程模型不再逐步看到。你會在哪些環節堅持保留逐步回報，又在哪些環節願意放手讓它批次執行？
  • 你部門最常被 agent 呼叫的內部系統（MES、良率資料庫、EDA log、license server），目前提供的是「回傳整張表」的大介面，還是可組合的小函式？要改成後者，第一步會是什麼？
  • 如果未來 agent 成本主要看「往返次數」而非「模型單價」，你會怎麼重新設計評估 agent 方案的指標，才不會被單價表誤導？

🎒 今日帶走：agent 變省不一定要換模型，讓它寫 recipe、少跑幾趟，再把裁判放在每一趟的終點。
