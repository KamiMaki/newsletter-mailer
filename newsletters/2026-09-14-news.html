🎯 今天的主軸
你桌上的 coding agent，本身成了新的攻擊面——這週三大工具修的不是「腦」，是「門鎖」

先講一個場景：你請了一位很能幹的裝潢師傅（AI coding agent）進家裡幹活。過去大家在意的是「師傅手藝好不好」——模型會不會寫程式。這一週三家大廠（Anthropic、OpenAI、Google）不約而同做的，卻是換門鎖、查證件、規定師傅帶來的水電工（MCP 工具）不能亂接管線。焦點從「代理夠不夠聰明」轉向「代理夠不夠安全地待在你的機器上」。

▍共同變化

三則更新指向同一件事：代理工具的本機權限模型被集中補強。
・Claude Code 2.1.269（9/11）→ 2.1.270（9/12）：修好幾個「deny／ask 權限規則會靜靜失效」的破口——以 ! 開頭的否定規則會外溢到寫它的設定檔以外、Edit() 與寫入路徑檢查擋不住 Bash tee 寫到工作目錄外的檔案；同時堵住 MCP／外掛連線細節把 ${VAR} 裡的密鑰印出來，並讓「未信任的工作區不載入 MCP 伺服器定義」。
・Gemini CLI 0.59.0：兩個安全修補——擋掉 MCP OAuth 中繼資料探索的 SSRF（伺服器端請求偽造），並改成「fail-closed 工作區信任」：沒信任過的資料夾，MCP 伺服器一律不載入。
・OpenAI Codex CLI 0.154.0：收緊啟動時的信任處理，並明訂外部訊息（ExternalMessage）只帶「工具層級授權，不等於使用者授權」——也就是外部塞進來的內容不能自動升級成你本人的權限。

▍為什麼放在一起看

單看是三則零碎的版本號，合起來卻是一條清楚的路線：agent 的價值來自「能讀你的檔、能跑指令、能接外部工具」，但這三件事正好也是它的攻擊面。三家在同一週把力氣花在同一組東西上——deny 規則、MCP 連線、工作區信任、密鑰外洩——這不是巧合，是整個產業意識到：把代理接進真實開發環境後，最大的風險不是它答錯，而是它被你剛 clone 的那個 repo 牽著走。

▍過去 vs. 現在

過去：「clone 下來直接開 agent」被當成順手的工作流，設定檔、hooks、MCP 伺服器清單只要在專案裡就會被讀。現在：三家都轉向「預設不信任（fail-closed）」——先問你信不信任這個工作區，沒點頭之前，專案內的 MCP／代理設定不生效。門從「預設開著」改成「預設鎖著」。

▍背後邏輯

這波修補的源頭，是稍早被揭露的一類真實漏洞：「信任前執行視窗」（pre-trust execution window）。Check Point 等研究指出，Claude Code 早期在你按下「信任這個 repo」之前，就會先執行 repo 內的設定，導致「光是 clone 並開啟一個惡意 repo」就可能偷走 API 金鑰或執行任意程式（對應 CVE-2025-59536、CVE-2026-21852，均已修補）。〔編輯分析〕把這條背景擺進來就懂了：MCP 讓代理能外接無數第三方工具，等於把「供應鏈風險」搬進你的終端機——工作區信任與 SSRF 防護，就是在補這道門。

▍對你的工作

如果你或團隊在跑這些 CLI：（1）升級到最新版，別停在舊版本吃這些破口；（2）檢查你寫在 /tmp、/var 這類符號連結路徑上的 deny 規則是否真的生效；（3）把 MCP 伺服器清單當成相依套件管理——只接你信得過的來源，並把密鑰放進真正的 secret 管理而非明文設定；（4）養成「先信任、再開工」的習慣，尤其是別人給你的 repo。

▍限制與待驗證

別誤讀成「已經安全了」。〔編輯分析／可能影響〕這些是「補洞」而非「重建」：deny 規則本質上是黑名單，補完一個繞法，往往還有下一個（見今日概念）。真正的安全邊界要靠允許清單＋沙盒隔離，而不是靠列舉所有壞路徑。另外「fail-closed 工作區信任」會改變你的手感——以後 clone 完不會立刻能用 MCP，得先明確信任；這是安全換來的一點摩擦，值得。

👤 人物觀點／延伸解讀

多位安全研究者示範過「用八種方式繞過自己的 Claude Code deny-list，最後只有 allow-list 守得住」「連下 50 個子指令後 deny 規則悄悄失效」等案例（延伸解讀，非官方發布）。這些不是官方事實，但和三家本週的修補方向完全對上：代理的權限不能靠「列黑名單」硬撐。

▍重點一句話

代理越能幹，它的「本機權限與外接工具」就越是攻擊面；這一週的主旋律是把門從「預設開著」改成「預設鎖著」。

📖 今日概念｜允許清單 vs. 拒絕清單（Allow-list vs. Deny-list）

一句定義：「拒絕清單」是列出所有禁止的東西、其餘放行；「允許清單」是列出所有准許的東西、其餘一律擋下。

生活化比喻：拒絕清單像夜店門口「這幾個人不准進」的黑名單——只要沒被點名、或換件衣服、走側門，就混得進去。允許清單像機場登機——名單上沒有你，怎麼樣都上不了飛機。

工作中的例子：今天主軸裡 Claude Code 修的那些 deny 破口——符號連結繞路、tee 寫到目錄外、否定規則外溢——本質都是「黑名單漏列了一種繞法」。你補一個，攻擊者找下一個；這是黑名單的宿命：你要枚舉「所有壞的」，但壞的無窮多。

常見誤解：「我把危險指令都 deny 了，應該安全了吧？」——不。deny 規則能減少誤觸，但不是安全邊界；真正的邊界是「只允許明確清單內的操作」＋沙盒隔離。方便的黑名單，換不到安全的保證。

與今天主軸的關係：三大 CLI 這週的方向，正是從「列黑名單」滑向「預設拒絕、明確允許」（fail-closed 工作區信任就是允許清單思維）。理解這條線，你就懂為什麼「補洞」永遠補不完，得換設計。

🏭 半導體 AI 專區｜用 AI 決定「測試點插哪裡」（DFT / 測試點插入）
分類：IC 設計 內容屬性：背景知識
▍問題與流程位置

晶片流片後要測「有沒有製造缺陷」，靠的是 DFT（可測試性設計）：在設計階段就把電路改造得「好測」。其中一步叫 測試點插入（Test Point Insertion, TPI）——在難以控制或難以觀察的內部節點加上額外的控制／觀測點，讓 ATPG（自動測試向量生成）更容易把缺陷「照出來」。痛點是：TPI 插太多會吃面積、增功耗、拖時序；插太少又測不乾淨。「插在哪、插幾個」是一個巨大的組合最佳化問題，傳統靠啟發式規則，常常顧此失彼。

▍AI 如何介入（與過去流程的差異）

〔背景知識〕過去是「規則＋工程師經驗＋反覆試跑 ATPG」的迴圈，一輪要很久。研究方向改用機器學習與強化學習：例如 DeepTPI 把電路轉成 And-Inverter Graph（AIG）圖表示，用深度強化學習學會「該把測試點放在哪」，目標是用更少的測試點換到更高覆蓋率、更少的 ATPG 向量數。差別在於：AI 能從大量電路中學到跨設計的通則，而不是每顆晶片都從零試錯——把原本幾輪 ATPG 才收斂的事，前移成一次較準的預測。

▍資料與產出

輸入：閘級網表／AIG 圖、節點的可控性與可觀測性指標、過往 ATPG 結果。產出：一組建議的測試點位置與型別，接回既有 DFT／ATPG 流程。近期也有像 ATPG-aware 輕量掃描插入（LITE）的做法，主打「比傳統 TPI 更低的面積／功耗代價」換到相近的測試效率。

▍如何驗證

關鍵是「AI 的建議不能只看它自己說好」——要用既有 ATPG 工具實跑，比較覆蓋率（fault coverage）、測試向量數、以及面積／功耗／時序 overhead 是否真的改善。這其實和今天主軸同一個精神：AI 提議、既有可信工具驗收，別讓提議者自己當裁判。

▍限制與風險

〔編輯分析〕學到的模型跨製程節點、跨設計風格的可遷移性有限，換一個 library 或設計團隊可能就要重訓；上述多為研究成果，不代表已大規模量產落地。真正導入時，覆蓋率與良率是不能妥協的紅線，AI 只能在「不劣化簽核結果」的前提下幫你更快收斂。

👷 對半導體工作者的意義：DFT／驗證工程師最有感——把 TPI 從「憑經驗反覆試」變成「先預測、再用 ATPG 驗收」。想動手的下一步，是拿自家一顆代表性設計，讓 ML 建議 vs. 現行流程做一次覆蓋率與 overhead 的對照，先看得到差距再談導入。
