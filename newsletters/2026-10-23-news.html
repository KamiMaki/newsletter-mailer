代理的「隨身技能」變成跨廠標準——四塊地基同搬進中立基金會，護城河從「我家的外掛格式」被抽走

今天代理圈的消息共同指向同一件事：讓 AI 代理「能幹活」的那幾塊底層規格，正在集體搬進一個中立的 Linux Foundation 基金會——Agentic AI Foundation（AAIF）。而今天（10/22–23，聖荷西）正是它的北美旗艦大會 AGNTCon + MCPCon 開幕日。

▍共同變化

把「代理怎麼運作」拆開，其實是四塊地基：MCP（Model Context Protocol，代理怎麼連外部工具與資料）、A2A（Agent2Agent，代理之間怎麼互相呼叫協作）、AGENTS.md（給代理看的專案設定檔）、以及 Agent Skills（把一套專業知識＋腳本打包成代理可隨取的「技能」，核心是一個 SKILL.md 檔案）。到今天，這四塊加上 Block 的 goose，全部歸到同一個中立基金會 AAIF 底下。Anthropic 今天把最後一塊 Agent Skills 整包捐出：名稱、logo、GitHub 組織、agentskills.io 網域一併移交。

▍為什麼放在一起看

單看一則「某標準捐給基金會」像行政新聞；四則擺在一起才看出趨勢：代理的擴充格式正在去私有化。MCP 是 Anthropic 去年捐的、A2A 是 Google 今年 8 月捐進來的、AGENTS.md 來自 OpenAI、goose 來自 Block——這些原本各家主推的格式，現在都交給一個誰都不獨佔的中立組織治理。AAIF 執行董事 Mazin Gilbert 把它定位成「代理式 AI 開放標準的中立之家」。

▍過去 vs. 現在

過去：你想讓代理多一項能力（例如「會查公司內部 API」），得照某一家的私有外掛格式寫，換一個平台就得重寫一次——像每個品牌手機各有自己的充電孔。現在：同一個 SKILL.md 寫好的技能，理論上能在 ChatGPT、Cursor、GitHub Copilot、VS Code 等 70+ 平台通用；一次寫好、到處能用。這就是代理生態的「USB-C 時刻」。

▍背後邏輯

當格式變成人人可用的中立標準，各家 AI 公司就無法再靠「我家獨有的外掛生態」綁住你。護城河被迫往兩層搬：一是模型本身（誰的推理更強），二是執行這些標準的平台體驗（誰把代理跑得更穩、更快、更好用）。對巨頭而言，捐出格式不是慈善——而是賭「標準通用後，真正的戰場在模型與體驗，而不是格式鎖定」，同時搶先把自家做法變成大家的預設。

▍對你的工作

對工程團隊，最實際的一句：別把工作知識鎖在單一工具或某幾位資深同事腦中。當「技能」變成可攜的開放格式，你團隊的檢查清單、流程規範、腳本，都可以包成跨平台都能索引的技能。對半導體讀者尤其有感——若 EDA 工具鏈採同一套互通標準，未來「設計流程的 agent」就能跨 Synopsys／Cadence／Siemens 搬動，而不是被綁死在某一家的私有格式裡（今天半導體專區用形式驗證的例子具體化這點）。

▍限制與待驗證

「標準」不等於「立刻好用」。各平台對同一份技能的解讀、權限與沙箱可能有差；把能力交給會自己執行腳本的代理，安全與供應鏈風險也隨之而來（AAIF 自己也把「技能作者與安裝者的安全指引」列進路線圖）。再者，捐出格式的同時各家仍以「個人身分」掌握維護權——Agent Skills 的 Lead Maintainer 是 David Soria Parra 與 Mahesh Murag，工程師來自 Anthropic／Google／OpenAI；中立治理能走多遠，仍待時間驗證。

👤 延伸解讀（編輯分析）

可以把這波類比成網路早期的 TCP/IP 與 HTTP：真正賺到錢的，很少是「定義協定的人」，而是「在協定上做出最好服務的人」。代理標準大合流，等於宣告「靠鎖死格式收租」這條路要收尾了；接下來值得盯的是——當格式不再是護城河，各家會把差異化押在模型、還是押在平台體驗？

▍重點一句話

代理的「隨身技能」正從「每家一套」變成「跨廠通用」——誰掌握標準不再靠鎖死格式賺錢，而是靠模型與體驗；把工作知識包成可攜技能，比綁在單一工具上更保值。

一句定義

系統先只給你「摘要／目錄」，等你真的需要時才載入完整內容；用在 AI 代理上，就是先讓模型看到「有哪些技能、各一句話」，只有被叫用的那個技能，才把完整指令與腳本塞進脈絡。

生活化比喻

像一本厚工具書——你不會把整本背進腦袋，而是先看目錄（一行行標題），要用哪章才翻哪章。Agent Skills 的 SKILL.md 檔頭（名稱＋一句描述）就是目錄，正文與附帶腳本是內頁。（說回技術：這其實是在管理模型有限的「脈絡視窗／token 預算」，避免一次塞爆。）

工作中的例子

把「公司驗證簽核流程」包成一個 skill：平常只占模型脈絡一行描述；當工程師真的要跑驗證時，代理才載入完整 checklist＋腳本去執行。模型「知道有這項能力」，但不必時時背著它的全文。

常見誤解

以為「給模型愈多資料＝愈強」。實際上脈絡塞太滿，會稀釋注意力、變慢變貴、也更容易出錯。漸進式揭露反其道而行——少即是多，按需取用。

與今天主軸的關係

Agent Skills 能成為跨廠標準、一次寫好到處能用，正因為它用「SKILL.md 一行描述＋按需載入」這種輕量格式——這個設計讓技能可攜、可被任何相容平台索引。標準能不能通用，往往取決於它夠不夠輕、夠不夠好接。

▍問題與流程位置

形式驗證（formal verification）是用數學證明電路在「所有可能輸入」下都符合規格，不像模擬只能跑有限測資。但它要工程師手寫大量斷言（assertion／SVA）——形式化的規則，例如「這兩個訊號永遠不能同時為 1」。寫斷言又慢又吃經驗，是驗證流程最耗人的瓶頸之一。位置：RTL 設計完成後、進入形式簽核時。

▍AI 如何介入

過去＝資深驗證工程師逐條手寫 SVA、再拿 JasperGold 等形式工具跑證明，失敗再回頭改。現在＝LLM 讀規格與 RTL 自動生成候選斷言，再把形式工具當成「迴圈裡的裁判」自我修正（例如把 Cadence JasperGold 當 solver-in-the-loop 的代理）。差異：把「寫斷言」從數天壓到數小時，並自動篩掉無效斷言。（編輯分析：這正是今日主軸的代理模式——代理在迴圈中呼叫外部工具，恰是 MCP／工具呼叫標準要處理的事。）

▍資料與產出

輸入＝設計規格（自然語言／文件）＋ RTL（Verilog／SystemVerilog）＋結構性中繼資料（flip-flop 時脈、reset 值、fanin／fanout、FSM 狀態編碼——這些正是 LLM 最缺、卻是驗證工程師仰賴的資訊）。產出＝可直接餵形式工具的 SVA 斷言集。

▍如何驗證

關鍵是避免「空洞斷言（vacuous assertion）」——永遠為真、卻沒抓到任何東西。學界做法：突變導引精煉（故意在設計裡種 bug，看斷言抓不抓得到，抓不到就淘汰）＋依 RTL 結構選最合適的 SMT 求解器＋把失敗反例轉成人看得懂的因果解釋（見 arXiv 2606.21451「Closing the Loop」）。

▍限制與風險

LLM 缺乏設計的結構性知識，易生出「過得了、但過錯原因」的斷言；證明成本在不同設計間差異巨大；目前多為學術框架與開源工具，尚非大規模量產簽核流程，不能當成已全面落地。
