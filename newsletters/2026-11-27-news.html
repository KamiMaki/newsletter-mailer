🎯 今天的主軸
多 agent 不是「人多好辦事」：先找瓶頸站、用同一份預算比，人守在驗收口

▍共同變化

過去一年，「多開幾個 agent 一起做」幾乎成了直覺：一個寫、一個審、一個查資料，好像人手越多越強。這兩天三份來自不同團隊的材料，不約而同地把這個直覺拆開來算帳——多 agent 的價值不在數量，而在編制：誰負責哪一站、站與站之間怎麼溝通、整體花了多少 token，以及最後由誰拍板。

▍為什麼放在一起看

用晶圓廠的語言最好懂：產線加機台，產能不一定上升，瓶頸站決定整條線的速度；換到 agent 系統，「機台」就是 agent，「瓶頸站」就是最常出錯、最花時間的那一步。三則消息剛好分別回答三個排班問題：

① 合作要練，而且要用同一份預算比。Hugging Face 11/26 的教學文用 4 個共用同一個 Qwen3-0.6B 權重的 agent，玩「各自拿一個 1–99 的私有數字、合力排出順序」的遊戲，並用一個會懲罰 token 用量的團隊獎勵去訓練。75 步內，成功率從 6.6% 升到 82.3%，每次嘗試的 token 從約 13k 降到 8k（−37.4%）；有趣的是互相廣播的次數反而從 2.38 增加到 5.73——話變多、但每句更精簡。作者特別強調，要拿「同樣 token 預算」跟單打獨鬥比：未訓練團隊用 best-of-8 硬撐，每題約 103k token 也只有 37.5%（作者標明為估算）。
🔗 閱讀原文 ｜ 來源：Hugging Face Blog

② 瓶頸站該放專用角色。阿里雲 11/26 公布 AgenticOps（自動化維運）的實測：在 1,745 題單一判斷上，9B 的「決策模型」Clef Pilot 準確率 82.81%，略勝通用模型 Qwen3.8 Flash 的 80.29%，P95 延遲則從 5.8 秒降到 1.15 秒。更關鍵的是放在哪一站：在完整根因分析流程中，放在「任務分派」站加 6.4 分、放在「進度評估」站加 7.2 分、放在「根因驗證」站只加 2.4 分；而原本流程有 54.7% 的模型呼叫時間花在「挑要看哪些物件與資料」。注意：完整流程只測 10 題，且是阿里雲評自家模型。
🔗 閱讀原文 ｜ 來源：Alibaba Cloud Blog

③ 人留在設定目標與驗收的位置。阿里雲同日整理的 7 個內部「AI 原生研發組織」案例，分工幾乎一致：agent 做執行、分析、重複工作；人訂目標、品質標準、權限、停止條件與驗收。其中資安團隊依風險分三級——標準清楚、可逆的事交給 agent 再由人核准；高風險、模糊或不可逆的留給專家；行銷案例則是「2 個人＋1 個 Leader Agent＋6 個 Worker Agent」的編制。以上數字均為阿里雲自述。

▍過去 vs. 現在

過去：多 agent 像臨時拉來的專案小組——每個角色用同一個大模型、靠一段角色提示詞區分，效果好不好看 demo。現在：開始像排產線——先量出哪一站最慢、最常錯，再決定那站放專用模型還是加人審；比較基準從「有沒有比單一 agent 強」變成「同樣 token 預算下有沒有比較強」；而合作本身是可以訓練、可以量測的能力，不是把 agent 放進同一個聊天室就會自然發生。

▍背後邏輯

多 agent 有兩筆隱形成本：溝通成本（每多一個成員，要傳的上下文與訊息就變多）與相關性成本（大家用同一個模型，容易一起犯同樣的錯）。所以單純加人，常常只是用更多算力換來同一個答案。真正的收益來自兩件事：把不同性質的工作切開，讓每站用「夠用就好」的模型（小模型便宜又快）；以及讓 agent 學會只傳必要資訊。這也是為什麼 Hugging Face 的獎勵設計要同時看「成功」與「token 用量」——沒有把成本寫進目標，團隊就會學會用話量換成績。

👤 人物觀點／延伸解讀

Hugging Face 文中引用 OpenAI 研究員 Noam Brown 的估計：OpenAI 那項 Navier-Stokes 成果中，來自多 agent 合作的貢獻不到一成。這是人物估計、不是量測結果，但提醒我們：看到「蜂群」大成果時，先問有多少功勞真的來自合作，而不是來自更多算力或更強的單一模型。🔗 來源（Hugging Face 引述）

▍對你的工作

如果你的團隊正在試「多 agent 跑驗證回歸」或「多 agent 整理良率報告」，先做三件事：一，畫出流程站點並量時間與錯誤分布，找出真正的瓶頸站（阿里雲案例中是「挑資料」，不是「寫結論」）；二，評估時把 token 或 GPU 時數一起記下，跟「單一 agent 多試幾次」放在同一預算下比較；三，依可逆性分級——改 testbench 註解可以讓 agent 自己來，改簽核用的 constraint 必須有人核准。

▍限制與待驗證

Hugging Face 的實驗是玩具任務（排序整數），能否推到寫程式或除錯仍未知；阿里雲的數字多為自家模型、自家案例自述，完整流程樣本只有 10 題，且作者自己承認部分組合會退步、排名受輸入整理方式影響。換句話說，「多 agent 有沒有用」目前高度依任務而定，沒有放諸四海的編制表。

▍重點一句話

加 agent 跟加機台一樣：先找瓶頸站、用同一份預算算產出，驗收口永遠要有人。

📖 今日概念｜阿姆達爾定律（Amdahl's Law）

定義

一件工作能加速多少，上限由「無法平行的那一段」決定：若 20% 只能循序做，就算其餘部分無限平行，整體最多只快 5 倍。

生活化比喻

十個人一起搬家，打包可以分工，但只有一台電梯；人再多，電梯那段的時間一秒都省不了。技術上，「電梯」就是必須循序執行的步驟——例如等待共享資源、彙整結果或人工核准。

工作中的例子

把回歸測試分到 100 台機器跑，模擬時間大幅下降，但 license 排隊、結果彙整與 waiver 審查仍是循序的；最後整體 turnaround 可能只快 3 倍，而不是 100 倍。

常見誤解

「資源加倍、速度就加倍。」實際上平行部分越快，循序部分占的比例越大；再加上溝通與協調開銷，加太多人甚至可能變慢。

與今天主軸的關係

多 agent 系統裡，「挑資料」「人工驗收」「彙整結論」就是那台電梯。與其多開 agent，不如先縮短循序段——這正是阿里雲把小模型放在「任務分派」這類關鍵站、以及 Hugging Face 訓練 agent 少說廢話的原因。

EDA 工具 近期研究（11/25）＋背景知識

▍問題與流程位置

背景知識：巨集擺放（macro placement）是實體設計很早的一步：先決定 SRAM、IP 這些大方塊放在晶片哪裡，再讓標準元件填進剩下空間。它像先擺好家裡的大型家具——一旦冰箱擋住走道，後面怎麼收納都彆扭；在晶片上，就是後段的繞線擁塞與時序收斂。麻煩在於，訓練時無法每試一次就跑完整流程，只能看「半周長線長」（HPWL，用每條線端點框起來的矩形周長估線長）這類快速近似指標，而它和最終 PPA 並不完全一致。

▍AI 如何介入

背景知識：傳統做法靠工程師經驗加上解析式擺放工具反覆調整；Google 的 AlphaChip 等研究則把擺放當成下棋，讓強化學習一步一步放方塊。但多數 RL 擺放器只追求「HPWL 最低的那一個解」，若那個解到了繞線階段才發現擁塞，就得重來。今日研究：11/25 上架的 DiversePlace 把「多樣性」寫進目標——維護一個小型候選庫，只收 HPWL 有競爭力、但彼此擺法明顯不同的解，用「品質門檻內才給多樣性獎勵」的 PPO 課程式訓練，從零開始學，不需要專家資料。

▍資料與產出

輸入是 netlist 與巨集尺寸，產出不是單一擺法，而是 top-5／10／20 個 HPWL 相近但布局不同的候選，讓下游時序、繞線、IR 分析去挑。

▍如何驗證

作者在公開基準 ISPD2005 的 8 個設計上，報告候選庫多樣性提升，HPWL 在全部設計上更低或幾乎相同、效率也更好（摘要未給具體數值）。

▍限制與風險

ISPD2005 是近二十年前的學術基準，規模與先進製程的約束（多電壓域、密集 SRAM、chiplet 介面）差很多；論文只用 HPWL 評估，尚未證明候選在實際繞線與時序上真的更好。編輯分析：它的價值在思路——當近似指標不可靠，與其押注一個最佳解，不如交出一組「一樣好但不同」的選項，把決定延後到資訊更多的階段。
