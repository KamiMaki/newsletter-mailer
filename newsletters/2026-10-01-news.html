🎯 今天的主軸
跑得動 agent 的，不是更聰明的模型，是每顆 GPU 每秒吐更多 token

這半年你大概被各種「更強的模型」轟炸到麻木。但把這 48 小時的新聞放在一起看，會發現大廠其實在悄悄換戰場——從「誰的模型更聰明」，換成「同樣一張 GPU，每秒能餵給 agent 多少 token」。打個比方：模型是廚師手藝，但當一整條街的客人（agent）從早到晚不停點餐，決定這家店能不能開下去的，是廚房出餐的速度與成本，不是廚師會不會做分子料理。

▍共同變化

9/30，NVIDIA 次世代 Vera Rubin NVL72 在雲端商 CoreWeave 正式進入「生產」——不是實驗室跑分，而是真的有付費客戶把工作跑上去。首個客戶正是做自主軟體工程師 Devin 的 Cognition。他們量到：跑自家 SWE-2（軟體工程）推論時，在相同互動速度下，每顆 GPU 的 token 吞吐量比上一代 GB200 高 4.8 倍；強化學習訓練的輸出吞吐則高 3.8 倍。同一天，OpenAI 的 GPT-6.1 Sol 以旗艦 Astra 五分之一的 token 價（約 $2 進／$10 出，每百萬 token）上架 GitHub Copilot、並成為 Codex CLI 預設；GitHub 的 HydraFusion 多模型編排也從 CLI 擴張到 VS Code。三件事看似無關，其實都在解同一題：怎麼讓一個整天在跑的 coding agent，成本不爆掉。

▍為什麼放在一起看

Cognition 創始團隊的 Silas Alberti 一句話點破了整條主線：「Agentic coding 是很麻煩的負載——長脈絡、高併發、龐大 token 量，每個 token 的成本，直接決定我們能出貨什麼。」這句話把三層新聞串成一條脈絡：晶片層（Rubin 把單卡吞吐拉高）、模型定價層（Sol 把單 token 價砍到五分之一）、編排層（HydraFusion 用「便宜模型先做、必要時才叫貴模型覆核」省錢）。大家從不同樓層往同一道牆鑿——因為 agent 不再是你按一下才回一句的聊天框，而是會自己連跑好幾個小時、吃掉數百萬 token 的常駐工人。

▍過去 vs. 現在

過去比模型，看的是「單題答得對不對」（pass@1、考試分數）。現在做 agent 產品，真正卡脖子的是每天能跑幾次、單位成本多少、延遲能不能撐住互動。CoreWeave 這批新機不只換 GPU，還換了搭配的 Vera CPU：每個機櫃能同時撐 11,000+ 個併發 agent 環境、沙箱啟動快 3 倍。這是一個很具體的訊號——agent 的瓶頸已經從「模型層」下沉到「基礎設施層」：CPU、記憶體、網路、沙箱啟動速度，這些過去沒人在意的東西，現在變成產品能不能跑的關鍵。

▍背後邏輯

為什麼是「吞吐量」而不是「峰值算力」？因為 agent 負載的特徵是長脈絡 + 高併發：每個 agent 都拖著一長串對話與工具呼叫的 KV 快取，記憶體先被塞爆，GPU 算力反而閒著。所以 Rubin 這代主打的不是「更會算」，而是更大的記憶體頻寬與更快的機櫃內互連（Spectrum-X 乙太網），把「餵資料」這件事做快。學界也在同一條線上——這個月 arXiv 一口氣冒出 ActKV、MemDecay、GraniKV 等一票論文，全在研究怎麼壓縮、驅逐、排程 agent 的 KV 快取，好讓同一張卡塞得下更多併發 agent。硬體、軟體、演算法，這回罕見地朝同一個目標對齊。

👤 人物觀點／延伸解讀

Cognition 的 Silas Alberti 強調「cost per token decides what we can ship（每 token 成本決定我們能出貨什麼）」。編輯分析：這句是 agent 經濟學的核心——當一個任務要燒掉數百萬 token，token 單價砍一半，等於讓原本賠錢的功能變成可以上線。這也解釋了為何 OpenAI 要拆出更便宜的 Sol、為何 GitHub 要做編排去「能省則省」：不是模型不夠強，是強模型太貴、跑不起量。

▍對你的工作

如果你在評估導入 coding agent 或任何 AI 工作流：別只看模型跑分，要看「每個完成任務的實際成本」與「尖峰併發撐不撐得住」。同一個模型，跑在新一代機器上、搭配對的編排策略，成本可能差好幾倍。對半導體人更直接：這波「吞吐量軍備賽」的受益者，是先進封裝（CoWoS／HBM 堆疊）、高速互連 IP、與網路晶片——Rubin 這類系統賣的其實是「整櫃的記憶體頻寬」，這正是台積電、封裝與網路供應鏈的訂單來源。

▍限制與待驗證

幾個要冷靜的地方：一，4.8 倍是 Cognition 自報、針對自家 SWE-2 負載，不是通用跑分，換個負載數字會變。二，CoreWeave 說 Rubin 目前是「限量供應、數百顆 GPU」，離大規模鋪開還早。三，「更便宜的 token」不等於「更便宜的任務」——如果便宜模型品質不夠、要來回重試，總成本反而可能更高，這正是 HydraFusion 這種編排要解、但還沒有公開數字證明有多划算的問題。

▍重點一句話

AI 的競爭正在從「模型腦袋」下沉到「推論水管」——決定 agent 能不能量產的，是每顆 GPU 每秒能吐多少 token，而這條水管的下游，正是半導體的先進封裝與互連。

📖 今日概念｜吞吐量 vs. 延遲（Throughput vs. Latency）
——以及為什麼要「在相同互動性下」才有意義

一句定義：延遲（latency）是「一個回應要等多久」；吞吐量（throughput）是「單位時間總共能處理多少」。兩者常常互相拉扯。

生活化比喻：想像高速公路。延遲＝一台車從頭開到尾要多久；吞吐量＝一小時通過收費站的車輛總數。你可以硬塞爆車流把「總通過量」衝高，但每台車都會塞到動不了（延遲爆掉）。反過來，只放一台車開最快，延遲最低、吞吐量卻慘不忍睹。說回技術：GPU 服務 LLM 也一樣——批次（batch）塞越多請求，總吞吐越高，但每個使用者等越久。

工作中的例子：今天 Cognition 說 Rubin「在相同互動性下，吞吐量 4.8 倍」——關鍵在「相同互動性」這五個字。意思是：他們把「每個使用者感受到的速度」固定住，才去比誰的總量大。這種「守住延遲再比吞吐」的指標，業界叫 goodput（有效吞吐），比單純報吞吐量誠實得多。

常見誤解：「吞吐量高＝跑得快」是錯的。一台每小時處理十萬 token、但每個請求要等 30 秒的系統，對互動式 agent 來說是不能用的。脫離延遲談吞吐量，等於脫離塞車談車流量。

與今天主軸的關係：主軸說「決勝點是每 GPU 吐多少 token」，但精確版本是——在使用者能忍受的延遲內，每 GPU 能吐多少 token（goodput）。這才是 agent 產品真正的成本函數。

▍問題與流程位置

今天主軸講 AI 幫人寫「軟體」程式碼。那 AI 能不能幫忙寫「硬體」程式碼——也就是描述電路的 Verilog／VHDL（RTL）？這一步位在晶片設計的最前端：工程師把規格（例如「做一個支援讀寫的 FIFO」）翻成 RTL，後面才輪到綜合、佈局、簽核。RTL 寫得慢、寫得錯，整條流程都得等。

▍AI 如何介入

過去要工程師逐行手刻；現在用 LLM 從自然語言規格直接生成 RTL。代表性研究如 CodeV、RTLCoder（開源方法）與評測 VerilogEval。跟 AI 寫軟體最大的差異是：軟體錯了頂多重跑，硬體錯了可能報廢一次幾百萬美元的光罩，所以 RTL 生成的重點不是「寫得快」，而是「寫得對、可驗證」。

▍資料與產出

輸入是規格描述（有時附介面定義、時序約束）；產出是可綜合的 Verilog 模組。訓練資料多來自開源硬體（如 OpenCores）。一個現實落差是：早期評測（如 VerilogEval V2）多為 76 行以下的自足小模組；而新一代的 ChipVerilog 用 OpenCores 真實 IP，模組動輒上千行、還有跨模組互動——這才接近工程師每天面對的複雜度。

▍如何驗證

生出來的 RTL 不能直接信。標準做法是模擬（跑測試向量比對波形）＋等價性檢查（LEC，與黃金參考比對邏輯是否一致）＋形式驗證。這正是為什麼「驗證優先」的多代理框架（先生、再自動寫 testbench、再形式檢查）成為近期研究主流——單靠 pass@1 分數高沒有意義，能通過簽核級驗證才算數。

▍限制與風險

編輯分析：目前 LLM 生 RTL 在教學級小模組表現亮眼，但在大型、有嚴格時序／功耗約束的真實設計上仍不成熟；且評測容易有「訓練資料汙染」（拿看過的題目考）。務實定位是「加速草稿與樣板、由工程師與驗證工具把關」，不是「自動流片」。官方與論文多半只敢說「探索中／研究成果」，切勿當成已大規模量產落地。

👷 對半導體工作者的意義：驗證與 DV 工程師受影響最直接——RTL 生成越普及，「機器可檢查的驗證流程」就越值錢；值得動手的下一步，是先在非關鍵模組試用 RTL 生成當草稿，並把 LEC／形式驗證掛成自動關卡，而不是急著讓 AI 寫關鍵路徑。
